## Milestone 3 Fix (2026-07-07): Chatbox / Display-Name Gate Root Cause
- **Real root cause was NOT a wrong Varbit/Varp — it was a sequencing bug.** 'Player.start()' (the
  shared login-finalize method, still used by both the legacy 184 path and RsProt) fires a burst of
  ONE-SHOT packets: 'packetSender.sendVarp(1737, -2147483648)', 'sendClientScript(1105, "i", 1)',
  '**sendClientScript(423, "s", name)**' (passes the player's own name — almost certainly the actual
  CS2 script that populates the client's display-name state), 'sendClientScript(2498, "i11", 1, 0, 0)',
  '**Config.HAS_DISPLAY_NAME.set(player, 1)**' (varbit 8199 -> resolves to its parent varp via
  'io.dm.cache.Varpbit', the SAME mechanism that already worked on the legacy 184 client),
  'sendClientScript(828, "i", 1)', and two 'sendClientScript(233, ...)' calls.
- 'RsProt.java's old 'doLogin()' called 'player.start()' at what is now line ~262 — BEFORE
  'DmLogin.INSTANCE.accept(...)' had created the RSProt 'Session'. 'PacketSender.queueRsprot()'
  (PacketSender.java:60) returns 'false' with no session, and every send method then falls through to
  the legacy 'OutBuffer'/'write()' path, which ALSO no-ops because RSProt players have a null Netty
  channel (PacketSender.java:42-48). Net effect: the ENTIRE one-shot burst above — including the
  '423' clientscript that sets the display name — was silently dropped for every RSProt login. Only
  varp/varbit writes made via 'Config.set()' survived even partially, because those go through
  'Player.updateVarp()' (dirty-tracking, Player.java:752) and get re-flushed every tick by
  'Player.sendVarps()' once the session exists — which is exactly why the earlier "toggle varp 1055"
  attempt visibly reached the client (it's dirty-tracked) yet still didn't clear the gate: **1055 was
  just the wrong number** (an unverified guess — 'Config.DISPLAY_NAME = varp(1055, true)' in
  Config.java is not a real cache-verified mapping), while the ACTUAL mechanism ('sendClientScript(423,
  "s", name)', an immediate non-dirty-tracked send) never reached the client at all.
- **Fix applied in 'DMS/src/main/java/io/dm/network/rsprot/RsProt.java' ('doLogin()'):**
  1. Removed the early 'player.start()' call (was right after 'player.newPlayer = false;') and the
     ineffective 'io.dm.model.inter.utils.Config.DISPLAY_NAME.set(player, 1)' varp-1055 hack alongside it.
  2. Re-inserted 'player.start()' AFTER the session-null check, 'RebuildLogin', 'setBuildAreas',
     'syncAppearance', and 'openFrame(s)' — i.e. after the RSProt session AND the game frame both
     exist, so 'queueRsprot()' actually queues every packet in the burst instead of dropping it.
  3. Left 'Config.HAS_DISPLAY_NAME' (varbit 8199) as the trusted, cache-verified flag — it was never
     the problem, it just needed its sibling clientscript (423) to actually arrive too.
- **Side benefit:** this also fixes the welcome message, 'LoginListener.executeAll()' UI, pet spawn,
  and daily-reset messages for RSProt players, which were equally being silently dropped by the same
  bug (all called from inside 'Player.start()').
- **Status: code-complete, NOT yet compiled or live-client-tested** (a compile check was in progress
  when this session ended). Next step before trusting this fixed: '(cd DeadMen-RSProt &&
  ./gradlew :DMS:compileJava)', then boot + RSProx login and confirm the "You must set a name..."
  overlay is gone and '::commands'/public chat work.

## Milestone 4 Fix (2026-07-07): Entity & Interface Interaction Wiring
- **Root cause:** 'RsProt.java's Consumer Registry (Phase E) only ever wired four incoming message
  types — 'MoveGameClick'/'MoveMinimapClick' (movement), 'ClientCheat' (::commands), and
  'MessagePublic' (chat). Every other decoded 'IncomingGameMessage' — every object, NPC, ground-item,
  and player click, every inventory/equipment/bank/interface button, and every item-on-X combination
  — fell through to 'DmIncomingPackets.registerNoOpsExcept's accept-and-drop no-op. The packet reached
  the server (so the client never desynced or errored), but no game logic ever ran: clicking anything
  in the world or on any interface was silently swallowed.
- **Fix applied in 'RsProt.java' ('start()'):** registered 11 additional real listeners, each a thin
  bridge from an RSProt-decoded message straight into the existing legacy Kronos handler under
  'io.dm.network.incoming.handlers.*' — no new gameplay logic was written; those handlers already
  fully implement this behaviour for the legacy 184 protocol (and still serve AI bots via that same
  path), they simply weren't reachable from RSProt-connected clients yet:
  - 'OpLoc' (object clicks, options 1-5) -> 'ObjectActionHandler.handleAction'
  - 'OpNpc' (NPC clicks, options 1-5) -> 'NPCActionHandler.handleAction'
  - 'OpObj' (ground-item clicks, options 1-5) -> 'GroundItemActionHandler.handleAction'
  - 'OpPlayer' (player clicks, options 1-8) -> 'PlayerActionHandler.handleAction'
  - 'If3Button' (every inventory/interface/equipment component click, options 1-10) ->
    'ActionButtonHandler.handleAction'
  - 'OpLocT'/'OpObjT'/'OpNpcT'/'OpPlayerT' (item- or spell-used-on-object/ground-item/npc/player) ->
    'InterfaceOnObjectHandler'/'InterfaceOnGroundItemHandler'/'InterfaceOnEntityHandler'
  - 'IfButtonT' (item-on-item, e.g. combining two inventory items) ->
    'InterfaceOnInterfaceHandler.handleAction'
  - 'IfButtonD' (interface drag, e.g. reordering inventory slots) -> 'InterfaceDragHandler.handleDrag'
- **Equip / unequip confirmed end-to-end, not just plumbed:** traced 'If3Button' all the way through
  'ActionButtonHandler.handleAction' -> 'InterfaceHandler.getAction(player, interfaceId, childId)' to
  the actual per-interface handlers. Interface 149 (Inventory) child 0's 'handleClick' is
  'TabInventory.click', which for `option == def.equipOption` (option 1 for ordinary gear) calls
  'player.getEquipment().equip(item)'. Interface 387 (Equipment) children 6-16 (one per worn slot) are
  'TabEquipment's 'itemAction', which for `option == 1` calls 'player.getEquipment().unequip(item)'.
  Both are reached automatically once 'If3Button' is wired — no separate equip/unequip-specific code
  was needed, only the dispatch path itself.
- **Why the plumbing "just fit":** decompiled RSProt's 'CombinedId' value class (bytecode, since only
  'osrs-228-model' ships sources — 'CombinedId' itself lives in the base 'protocol' artifact) and
  confirmed `combinedId = ((interfaceId and 0xffff) shl 16) or (componentId and 0xffff)`, with 0xffff
  ("no value") normalized to -1 on the way out — bit-for-bit the same packed format and sentinel
  convention as the legacy `interfaceHash` parameter every 'ActionButtonHandler'/'InterfaceHandler'/
  'InterfaceOn*Handler' method already takes. So 'msg.getCombinedId()' (or '.getSelectedCombinedId()'/
  '.getTargetCombinedId()' on the *T/'IfButtonD'/'IfButtonT' variants) drops straight into those
  existing parameters with no translation code required.
- **Visibility widened on 8 legacy handler methods, behaviour untouched:** 'NPCActionHandler',
  'PlayerActionHandler', 'GroundItemActionHandler', 'InterfaceOnObjectHandler',
  'InterfaceOnGroundItemHandler', 'InterfaceOnEntityHandler', 'InterfaceOnInterfaceHandler', and
  'InterfaceDragHandler' each kept their real per-option logic in a 'private' (one 'protected') static
  method, reachable only via their own 'handle(Player, InBuffer, int)' entry point in the same package.
  Widened each to 'public static' (pure visibility change, no logic touched) so 'RsProt.java' — in a
  different package — can call them directly with RSProt's already-decoded fields.
  'PlayerActionHandler's private 4-arg 'handle' was additionally renamed to 'handleAction' (its two
  internal call sites updated to match) purely so all four entity-action handlers
  (Object/NPC/Player/GroundItem) share one consistent public entry-point name.
- **isLocked()/resetActions() guard duplicated, not moved, for four of the eight:** 'ObjectAction-',
  'NPCAction-', 'GroundItemAction-', and 'PlayerActionHandler' each apply
  `if(player.isLocked()) return; player.resetActions(true, true, true);` inside their
  'handle(Player, InBuffer, int)' entry point, BEFORE calling into the now-public 'handleAction' this
  milestone bridges into directly — so calling 'handleAction' straight from RSProt would have skipped
  that guard entirely (RSProt players could then fire object/npc/player/ground-item actions while
  stunned/busy/mid-dialogue, or stack actions without clearing the previous one). Rather than move the
  guard into 'handleAction' itself — which would also strip it from those classes' own inline
  'option == 6' (examine) branch, changing existing legacy-184/AI-bot behaviour — each new
  'RsProt.java' bridge method ('onObjectAction'/'onNpcAction'/'onGroundItemAction'/'onPlayerAction')
  duplicates the same two-line guard before calling 'handleAction', leaving the legacy entry points
  completely untouched. The other four handlers ('ActionButtonHandler', 'InterfaceOnGroundItem-'/
  'InterfaceOnObject-'/'InterfaceOnEntity-'/'InterfaceOnInterfaceHandler', and 'InterfaceDragHandler')
  needed no duplicated guard: the first never gated button clicks behind 'isLocked' in the legacy path

## Milestone 4 Fix — Live Testing Round 1 (2026-07-08)
- **First live-test pass reported broken:** wield, drop, inventory limited to visually one item

  exposed a fourth. Equip/drop/drag and the bank interface are **still broken** after all of this —

- **Bug 1 — login never registered the fixed-frame panes as "visible."** 'RsProt.java's
  'openFrame(Session)' queued raw 'IfOpenSub' messages directly (`s.queue(new IfOpenSub(...))`)
  instead of calling 'PacketSender.sendInterface(...)'. That matters because 'sendInterface' does two
  things, not one: it sends the packet *and* calls 'player.setVisibleInterface(interfaceId, parentId,
  childId)' — the bookkeeping 'InterfaceHandler.getAction' checks (via 'isVisibleInterface') before
  running any click handler. Bypassing it meant every fixed-frame pane (inventory 149, equipment 387,
  prayer 541, etc.) rendered correctly on screen but was permanently "not visible" server-side, so
  every click on any of them silently no-opped — explaining wield/drop/drag/interfaces uniformly.

  'player.getPacketSender().sendGameFrame(FIXED_TOP_LEVEL_INTERFACE)' +
  '.sendInterface(pane[0], FIXED_TOP_LEVEL_INTERFACE, pane[1], 1)' per pane, reusing the same
  already-ported, already-correct methods the rest of the game uses to open interfaces (bank, shops,
  etc.), instead of hand-building RSProt messages a second time.
- **Bug 2 — that fix immediately crashed login with an "Index 80 out of bounds for length 80"
  'ArrayIndexOutOfBoundsException' in 'Player.setVisibleInterface'.** Root cause: 'setVisibleInterface'
  sizes its 'visibleInterfaceIds[parentId]' bookkeeping array from 'InterfaceDef.COUNTS[parentId]' —
  and 'InterfaceDef.COUNTS' is loaded from `Server.fileStore.get(3)`, the **legacy** (older-revision)
  cache, per the existing "JS5 cache is a separate FileStore" note above. The legacy cache reports
  interface 548 (the game frame) as having 80 children. The real 228 client's interface 548 has more —
  the fixed-frame-pane table (sourced from AlterRSPS, a modern-228 reference) uses child slots up to
  93 for skills/quest/inventory/equipment/prayer/magic/clan chat/etc. The very first pane whose slot
  (80, "combat options") reached that ceiling threw immediately, taking the whole login down with it.
  This mismatch was always latent — it just had nothing to trip it until Bug 1's fix started actually
  calling 'setVisibleInterface' for every pane. **Fix:** 'setVisibleInterface', 'removeVisibleInterface',
  'isVisibleInterface', and 'moveVisibleInterface' in 'Player.java' now grow 'visibleInterfaces'
  (flat array) and each 'visibleInterfaceIds[parentId]' (per-parent child array) on demand instead of
  trusting the legacy cache's counts are complete — a general fix, not a special case for interface
  548, so it should also protect any other interface whose real (228) child/id range exceeds what the
  legacy cache reports.
- **Bug 3 — inventory partial updates always wrote to slot 0.** Reported as "inventory limited to a
  single item / spawning a new item overrides the first item." Root cause in
  'PacketSender.updateItems()': the 'UpdateInvPartial.IndexedObjectProvider.provide(slot)' callback
  returned 'InventoryObject.pack(it.getId(), it.getAmount())' — the **2-arg** overload. Decompiling
  'InventoryObject' (bytecode; 'osrs-228-common' has no published sources) showed 'pack(int, int)' is
  literally `pack(0, id, count)` — it always packs slot **0**. That's correct for 'UpdateInvFull' (full
  syncs are positional: slot = position in the stream, the packed value's own slot bits are never
  read), but 'UpdateInvPartial' is sparse — its own 'buildInventory' loop asserts
  `InventoryObject.getSlot(obj) >= 0`, i.e. it reads the slot back out of the packed value itself. So
  every partial update — regardless of which real slot changed — told the client "slot 0 changed,"
  and every new/changed item visually replaced whatever was already in slot 0. **Fix:** use the 3-arg
  'InventoryObject.pack(slot, id, count)' for the populated-item branch, and 'pack(slot, -1, -1)'
  (RSProt's own documented "empty slot" form for partial updates, per its 'check()' message) instead
  of the bare 'NULL' sentinel for the removed/invalid-item branch — 'NULL' has no slot embedded either
  and would have had the same "can't tell the client which slot to clear" problem for removals.

## STAGE 02 — Ground items spawn, render, and despawn (2026-07-08)
- **Root cause found, deeper than the 2026-07-07 zone-coordinate fix: RSProt players were never
  added to any `Region`'s `players` list at all.** `GroundItem.sendAdd()`/`sendRemove()` (and, it
  turns out, several other systems — see below) loop over `tile.region.players` to decide who to
  send a packet to. That list is populated ONLY by `Player.addRegion()`, which itself was ONLY ever
  called from the legacy `PacketSender.sendRegion()` (packets 66/71, a wire format the rev-228
  client doesn't speak and RSProt sessions never trigger). Net effect: for every RSProt player,
  every `Region` they were ever "in" had zero entries for them, so `GroundItem.sendAdd()`'s loop
  matched nobody and never even called `sendGroundItem()` — independent of whether the packet was
  ported correctly or the zone coordinates were right. This fully explains Stage 01's live-tested
  "still completely broken after the x&~0x7 fix" finding.
- **Fix applied in `RsProt.java`:** added `syncRegionTracking(Player, zoneX, zoneZ)`, a private
  static helper that mirrors the region-grid math from legacy `PacketSender.sendRegion()`'s
  regular-map branch (chunk/zone are both 8-tile units; `depth=6` matches `CLIENT_SIZE>>4`) but
  skips building the legacy OutBuffer packet — it just calls `player.removeFromRegions()` then
  `player.addRegion(region)` for every 64x64-tile `Region` overlapping the player's current 13x13
  zone viewport, then calls `Region.update(player)` (the existing legacy method that resends ground
  items + custom objects for every active tile in the player's tracked regions — already correct,
  just never reached because the region list was always empty). Called from two places: `doLogin()`
  right after `setBuildAreas()` (so a fresh login picks up anything already on the ground nearby),
  and `maybeRebuildRegion()` right after it sends `RebuildNormal` (so walking into a new area
  resyncs ground items/objects for the newly-loaded zones — this is what makes the "walk away, walk
  back, item still there" test-script point work, since the client's own scene gets rebuilt on
  `RebuildNormal` and needs the resend to repopulate it).
- **Ported `ObjDel` for `sendRemoveGroundItem`** (previously had NO RSProt path at all — silently
  fell through to the legacy `sendMapPacket`, which no-ops for RSProt's null Netty channel).
  Constructor `ObjDel(id, quantity, xInZone, zInZone)` verified directly against the
  `osrs-228-model` sources jar, same pattern as every other zone payload. This also matters for the
  new `syncRegionTracking`/`Region.update()` path above: `Tile.update()` sends a remove-then-add
  pair to resync each ground item, so without `ObjDel` ported, every resync would have thrown an
  extra silently-dropped removal instead of round-tripping cleanly.
- **Ported `LocAnim` for `sendObjectAnimation`** while in the same file with the same sources jar
  open (flagged as cheap-to-add-in-passing by the stage brief, not a Stage 02 requirement) —
  `LocAnim(id, xInZone, zInZone, shape, rotation)`, same `type`/`dir` → `shape`/`rotation` mapping
  already used by `sendCreateObject`/`sendRemoveObject`.
- **Broader impact discovered, flagged to other stages, not fixed here (out of this stage's
  scope):** `tile.region.players` is also the send-target list for `GameObject.spawn()`/`setId()`
  (dynamic object add/remove — e.g. a chopped-down tree, an opened door's object swap),
  `Door.java`'s direct object-update send, `WildernessObelisk.java`, and `MotherlodeMine.java`. All
  of these were equally broken for RSProt players before this fix and should now work once
  `syncRegionTracking` is populating `Region.players` correctly — added a note to
  `stages/STAGE-07-object-interactions.txt` so whoever picks that stage up doesn't misattribute a
  now-fixed rendering gap to their own in-progress work.

### Round 2 (same day) — human reported "ground items still do not work in any capacity"
- **Found and fixed a SECOND, independent root cause — the region-tracking fix above was necessary
  but not sufficient.** Re-examined `PacketSender.queueZonePayload` (the shared helper behind all
  six zone-scoped sends) against `UpdateZonePartialEnclosed`'s actual field types in the sources
  jar, not just its KDoc prose: `_zoneX`/`_zoneZ` are declared `UByte` (0-255). The KDoc's worked
  example — "player at absolute coordinate of 50, 40 *within the build area (104x104)*" — makes
  clear that "absolute, not shifted" only disambiguates from the divided-by-8 zone-index form; the
  coordinate itself is still relative to the player's 104x104 build-area origin, not the world's
  absolute tile grid. The 2026-07-07 fix (`x & ~0x7`) removed the wrong shift but never subtracted
  the build-area origin, so it was still passing a raw world-tile value (typically in the low
  thousands) into a field that silently truncates mod 256 — e.g. world zone-corner 3216 truncates
  to 144, still outside the valid 0-104 window. Every zone-scoped packet was landing on an
  effectively arbitrary wrong zone, independent of the region-tracking bug above; both had to be
  fixed for anything to render.
- **Fix applied in `PacketSender.queueZonePayload`:** `x & ~0x7, y & ~0x7` →
  `(x & ~0x7) - (player.buildAreaZoneX << 3), (y & ~0x7) - (player.buildAreaZoneZ << 3)`. This
  mirrors a transform already proven correct elsewhere in this exact codebase —
  `RsProt.driveUpdate()`'s `SetNpcUpdateOrigin(x - (p.buildAreaZoneX << 3), z - (p.buildAreaZoneZ
  << 3))` — and, worked through by hand for a player near their build-area centre, reproduces the
  KDoc's own example numbers (48) almost exactly, which is a strong sanity check that this reading
  of the doc is the correct one.
- **Because this is the same shared `queueZonePayload` helper, this fix applies to all six
  zone-scoped sends at once** — ground items, object add/remove/animate, projectiles, graphics, and
  area sounds. Flagged prominently in `stages/STAGE-10-player-fx-verification.txt` (which owns
  live-verifying projectiles/graphics/area sounds) and added a follow-up note to
  `stages/STAGE-07-object-interactions.txt` (dynamic object add/remove uses the same helper).

## STAGE 03 — NPC spawning (2026-07-08)
- **Goal:** NPCs (Lumbridge spawns etc.) never rendered to a rev-228 client at all. Root cause
  (already diagnosed in `stages/STAGE-03-npc-spawning.txt` before this session started): per-player
  `NpcInfoProtocol` was wired (alloc'd at login, driven every tick), but nothing ever allocated a
  global `NpcAvatar` for any server-side `NPC` — `NpcInfoProtocol` can only report NPCs that have an
  avatar; with none allocated, the outgoing NPC-info packet was permanently empty.
- **API (from `osrs-228-model`'s sources jar + `javap` on `osrs-228-api`):**
  `NetworkService.getNpcAvatarFactory()` → `NpcAvatarFactory`. `.alloc(index, id, level, x, z,
  spawnCycle, direction, priority, specific)` → `NpcAvatar` (only index/id/level/x/z/direction are
  passed here; spawnCycle=0, priority/specific left at their `@JvmOverloads` defaults). `.release
  (avatar)` frees it back to the pool. `NpcAvatar.teleport(level,x,z,jump)` / `.walk(deltaX,deltaZ)`
  (single-tile only, -1..1, not both 0) drive position; `.setInaccessible(boolean)` hides/shows
  without deallocating. `Direction.ordinal()` (this codebase's own enum) already matches RSProt's
  0-7 NPC direction table exactly — verified by reading both tables side by side, no translation
  needed.
- **Implementation:** `NPC.java` gained a public `NpcAvatar rsprotAvatar` field. `spawn()` calls the

  the new `RsProt.deallocNpcAvatar(this)` before freeing the world-list slot. A new `NPC.setHidden()`

  getters), the `allocNpcAvatar`/`deallocNpcAvatar`/`pushNpcMovement` static methods, and a new step

## STAGE 03 follow-up — NPCs spawn but don't wander (2026-07-08)
- Human live-tested Stage 03: NPCs now render and are visible at Lumbridge (the avatar-allocation fix
  worked), but no NPC ever wandered.
- **Root cause:** `NPC.isRandomWalkAllowed()` gates random walking on `localPlayers().size() != 0`.

- **Fix:** new `PlayerNPCUpdater.syncLocalNpcs()` extracts just the local-list add/remove membership

## Stock Cache228 Migration & Boot Fixes (2026-07-12)

### Trigger
The user discovered that `cache_path` in `DMS/server.properties` still pointed at `../Cache` — the
old, hand-customized 184-era cache this project has used for years — despite everything the RSProt
migration implies about "rev 228." Only `js5_cache_path` (the JS5 stream served to real rev-228

`AnimDef`, `GfxDef`, `ScriptDef`, region map/landscape data, everything `Server.java`'s boot
sequence loads — was still reading the OLD cache the whole time. The user renamed `Cache/` to
`Cache_ANTHING` to prove the point (if the server still booted fine while that path didn't
resolve, something must have been silently falling back to it or never actually depending on it as
claimed), then set both `cache_path` and `js5_cache_path` to `../Cache228/cache` and gave two
explicit standing instructions: **the cache must remain stock — no re-patching it, ever** (this was
already established practice per the Round 8 "Use"-text revert, Milestone 4 above — just now
stated as a hard rule rather than a one-off decision) — **and any game content that turns out to
depend on ids that only ever existed in the old custom cache gets disabled outright, not
null-guarded into limping along.**

### Method
Boot the server, read the first real exception, fix the actual root cause (not a try-catch around
it), rebuild, reboot, repeat. Every fix below was verified by reading the relevant source, and
where the cause wasn't obvious from the stack trace alone, by adding a throwaway diagnostic,
rebuilding, and reading real output — not guessed. Two hypotheses were explicitly tested and
disproven with evidence rather than assumed (see "Region-decrypt investigation" below) — worth
calling out because guessing-then-asserting is exactly the failure mode this session was trying to
avoid, per explicit user instruction ("DO NOT SKIP ANYTHING, FIX IT").

### Bugs fixed (real, cache-independent — would have crashed on ANY cache, just never triggered)
- **`ScriptDef.load()` (`DMS/src/main/java/io/dm/cache/ScriptDef.java`) crashed the entire loader —
  taking the whole server boot down with it — the instant one CS2 script archive failed to decode.**

  large enough to contain the fixed 12+-byte trailer `decode()` requires — a genuine empty/

  hand-tuning a `minSize` per call site (the existing 3-arg `register(id, minSize, consumer)`

sendPlayerHead`, `.sendNpcHead`, and `.animateInterface` were three of the very few remaining
send methods in the entire file with NO RSProt branch at all — every other ported method in this
class (`sendString`, `setHidden`, `sendItem`, `sendAccessMask`, `sendClientScript`, etc.) starts
with `if (queueRsprot(new net.rsprot.protocol.game.outgoing.interfaces.IfSetXxx(...))) return;`
before falling through to the legacy 184 `OutBuffer` path; these three skipped straight to
`write(out)`, and `write()`'s own existing comment spells out the consequence: RSProt-bound real
players have a null legacy Netty channel by design, so `if (player instanceof AIPlayer ||
player.getChannel() == null) return;` silently drops the packet. The three calls in
`NPCDialogue.open()`/`PlayerDialogue.open()` (added correctly in Round 1, retargeted to the
correct child 2 in Round 2) were therefore complete no-ops for every rev-228 client that has ever
connected to this server — a gap that predates Stage 11 entirely (Milestone 4's original 11-
listener wiring never touched outbound `PacketSender` methods, and nothing in Stages 01-10
exercised chat heads specifically enough to surface it). Confirmed via grep that
`sendPlayerHead`/`sendNpcHead`/`animateInterface` have exactly one caller pair in the whole repo
(NPCDialogue + PlayerDialogue), so the bug's blast radius is exactly the reported symptom, nothing
wider.
