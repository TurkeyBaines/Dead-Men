## Milestone 1 Fix (2026-07-07): Zone-Scoped Payload Port
- **Added 'queueZonePayload(x, y, level, ZoneProt)' to 'PacketSender.java'** (mirrors the existing
  'queueRsprot(msg)' pattern): builds the single payload sub-message (one of 'ObjAdd', 'LocAddChangeV2',
  'LocDel', 'MapAnim', 'MapProjAnim', 'SoundArea'), encodes it via
  'DesktopUpdateZonePartialEnclosedEncoder.Companion.buildCache(allocator, List.of(payload))' into a
  ByteBuf, wraps that in 'new UpdateZonePartialEnclosed(zoneX, zoneZ, level, buf)' (zoneX/zoneZ = x/y
  >> 3), and queues it on the player's session — same "return true to skip the legacy OutBuffer path,
  false falls through" contract as every other ported send method.
- **Gradle fix required — this was the actual compile blocker:** 'net.rsprot:osrs-228-api' (the
  dependency 'dm-net/build.gradle' declares) only exposes 'osrs-228-common' + 'osrs-228-model' on its
  *compile* classpath per RSProt's own published Gradle module metadata; 'osrs-228-desktop' (where
  'DesktopUpdateZonePartialEnclosedEncoder' lives) and 'osrs-228-internal' are wired **runtime-only**.
  Fixed by adding both as explicit 'api' dependencies in 'dm-net/build.gradle' so they flow through to
  ':DMS'. Since this server only ever allocates DESKTOP client sessions (HANDOFF.txt already notes
  'PlayerInfoProtocol.alloc(index, DESKTOP)'), depending on the desktop codec module directly is
  correct, not a workaround.
- **Revision-mismatch caught mid-implementation:** the first draft of 'sendProjectile' was written
  against RSProt rev 239's API ('MapProjAnimV2'), which doesn't exist in rev 228 — this project targets
  228 ('dm-net/build.gradle: ext.rsprotRev = "228"'). Corrected to rev 228's actual 'MapProjAnim' class,
  which has a materially different field layout: relative 'deltaX'/'deltaZ' offsets from the start tile,
  not an absolute end 'CoordGrid' like the 239 class. All six classes' constructor parameter orders were
  re-verified directly against decompiled bytecode of the real jars this project depends on
  ('net.rsprot:osrs-228-{model,desktop,internal}:1.0.0-ALPHA-20260630') rather than trusted from name
  similarity alone.
- **Best-effort field mappings still needing live-client confirmation** (compile-safe, semantics
  unconfirmed): 'sendProjectile's legacy 'curve'/'something' bytes map positionally onto RSProt's
  'angle'/'progress' fields (no exact legacy-name match); 'sendAreaSound's legacy 'type'/'distance'
  fields map onto 'loops'/'range'+'dropOffRange' the same way. Every other mapping (ground items, object
  add/remove, graphics) is a direct 1:1 field correspondence with no ambiguity.
- **Status: code-complete, compiles clean (2026-07-07).** Not yet live-client-tested — next step is
  booting the server + RSProx and confirming ground items, object placement/removal, graphics, area
  sounds, and projectiles all render correctly, paying closest attention to projectile arc/curve and
  area-sound falloff since those two used the positional best-effort mapping above.

## Milestone 2 Fix (2026-07-07): Player Update Mask → PlayerAvatarExtendedInfo Bridge
- **Added 'RsProt.pushMaskUpdates(Player)'**, called once per online RSProt player as a new "step 0"
  at the top of 'RsProt.driveUpdate()' — runs before step 3's 'playerInfoProtocol.update()' gathers
  each avatar's currently-flagged extended-info blocks into that cycle's snapshot. Reads each of the
  11 player-applicable legacy masks (of the 12 classes in 'model/entity/shared/masks/'; the 12th,
  'TransformUpdate', is NPC-only — never instantiated in 'Player.init()'s 'masks[]' array, so there is
  nothing to bridge for players there) and calls the matching 'PlayerAvatarExtendedInfo' setter:
  'AnimationUpdate'->'setSequence(id,delay)'; 'GraphicsUpdate'->'setSpotAnim(0,id,delay,height)'
  (legacy only ever has one graphic slot, so slot 0 is a fixed constant, not a guess); 'HitsUpdate'->
  'addHitMark(...)' per queued splat + 'addHeadBar(...)' for the hp ratio; 'ChatUpdate'->'setChat(...)';
  'EntityDirectionUpdate' (face entity)->'setFacePathingEntity(...)'; 'MapDirectionUpdate' (face
  angle)->'setFaceAngle(direction)'; 'ForceTextUpdate'->'setSay(forceText)'; 'ForceMovementUpdate'->
  'setExactMove(...)'; 'MovementModeUpdate'->'setMoveSpeed(mode)' (values 1=walk/2=run match RSProt's
  own numbering exactly, confirmed against the call sites in 'PlayerMovement.java'); 'TeleportModeUpdate'
  ->'setTempMoveSpeed(mode)' (only ever called with 127, RSProt's own "Teleport" sentinel — exact
  match, not a guess); 'Appearance'->re-invokes the existing 'syncAppearance(player)' (already used at
  login) whenever 'Appearance.hasUpdate(false)' is true, so equipment/title/combat-level changes
  mid-game now also reach RSProt, not just the initial login snapshot.
- **Getters added to 8 mask classes** ('GraphicsUpdate', 'HitsUpdate', 'ChatUpdate',
  'EntityDirectionUpdate', 'ForceMovementUpdate', 'ForceTextUpdate', 'MapDirectionUpdate',
  'MovementModeUpdate', 'TeleportModeUpdate') plus 8 new pass-through getters on 'Entity'/'Player'
  (mirroring the pre-existing 'getAppearance()'/'getChatUpdate()' pattern) so 'RsProt.java' — which
  already reaches into 'Player'/'Appearance'/'Equipment' for 'syncAppearance()' — can read the other
  10 masks the same way. Purely additive; no existing field or method signature changed.
- **'ChatUpdate' needed an actual fix, not just a getter, for the bridge to be possible at all:**
  'set()' immediately Huffman-encodes the message into 'messageData' and never kept the plaintext
  anywhere, so there was no string left for RSProt's self-encoding 'setChat(...)' to consume. Added a
  'message' field, populated from the same case-fixed string that gets encoded, so both paths render
  identical text. (In practice, real RSProt players' own public chat already renders via a separate,
  already-working path — 'RsProt.onPublicChat()' bridges the incoming 'MessagePublic' straight to
  'setChat()' before this mask is ever touched; 'ChatUpdate' itself is currently only populated by the
  legacy-184 'ChatHandler.java', i.e. AI bots / non-RSProt connections. Bridged anyway per this
  milestone's explicit "Chat" requirement, and in case anything else starts writing to it later.)
- **'EntityDirectionUpdate' (face-entity) needed real behavioral thought, not just a passthrough:**
  two separate issues, both fixed:
  1. *Index-space mismatch:* the legacy 'direction' field stores 'Entity.getClientIndex()'s encoding
     (players = realIndex + 32768, NPCs = realIndex), but RSProt's 'setFacePathingEntity' expects
     players = realIndex + 0x10000 (65536). A raw passthrough would have put every player face-lock
     roughly 32768 too low — landing in, and potentially colliding with, the NPC index range instead
     of the player range. Fixed with 'RsProt.toRsProtEntityIndex()', which re-derives the real index
     and re-encodes it in RSProt's own scheme.
  2. *Delayed-remove quirk doesn't apply to RSProt:* 'faceNone(true)' (used a lot — e.g.
     'PlayerCombat.java:638' on every non-death combat disengage) delays the actual 'direction' field
     flip by up to 2 game cycles via an internal 'stage' counter, solely to work around a legacy 184
     client quirk. Replicating that delay for RSProt would add a real, visible 2-tick lag to un-facing
     that the modern client doesn't need. Added 'resolvedTarget'/'consumeResolvedUpdate()' to
     'EntityDirectionUpdate', updated immediately by both 'set()' and 'remove()' regardless of the
     'delay' flag, so the RSProt bridge reflects the game logic's actual intent ("stop facing now")
     instead of the 184-specific staging artifact. The existing 'direction'/'stage'/'sent' state
     machine driving the legacy 184 encoder is untouched.
- **Caught a "replays forever" bug before it shipped:** 'Entity.resetUpdates()' only calls a mask's
  'reset()' once 'isSent()' is true, and the ONLY place that ever called 'setSent(true)' was the
  legacy 'PlayerUpdater.writeMasks()' — which 'CoreWorker.update()' explicitly skips for RSProt
  players ('if(player.getSession() == null)'). Without 'pushMaskUpdates()' also calling 'setSent(true)'
  itself on every mask it consumes, 'hasUpdate(false)' would never go false again after the first
  trigger, and this bridge would have replayed the same animation/graphic/hitsplat/chat/etc. every
  single tick forever instead of once. Fixed by calling '.setSent(true)' at the end of every branch
  (except face-entity, which self-tracks via 'resolvedDirty' independently of 'sent'/'reset()') so the
  existing 'resetUpdates()' cleanup — already called once per cycle for every online player,
  regardless of transport — correctly clears these masks too.
- **Hit-source tinting is a known best-effort gap** (same spirit as the curve/progress and
  type/loops notes under "Milestone 1 Fix" above): 'HitsUpdate.add()' only ever kept a hit's 'type'
  ordinal + 'damage' in its private 'Splat', never the attacker. 'addHitMark'/'addHeadBar' are
  therefore pushed with 'sourceIndex = -1' — damage numbers and the hp bar render correctly for
  everyone, but nobody gets the attacker-tinted hitmark variant. Would need 'Hit.attacker' threaded
  through 'Splat' (and through the same client-index re-encoding as face-entity above) to close.
- **Status: code-complete, compiles clean (2026-07-07)** ('./gradlew :DMS:compileJava'). Not yet
  live-client-tested — next step is booting the server + RSProx and confirming animations, spot-anims,
  hitsplats/hp bar, force-text/chat bubbles, face-entity/face-angle, and forced movement all render on
  a real RSProt-connected character, the same live-verification step Milestones 1 and 3 are also still
  waiting on.

## Milestone 3 Fix (2026-07-07): Chatbox / Display-Name Gate Root Cause
- **Real root cause was NOT a wrong Varbit/Varp — it was a sequencing bug.** 'Player.start()' (the
  shared login-finalize method, still used by both the legacy 184 path and RsProt) fires a burst of
  ONE-SHOT packets: 'packetSender.sendVarp(1737, -2147483648)', 'sendClientScript(1105, "i", 1)',
  '**sendClientScript(423, "s", name)**' (passes the player's own name — almost certainly the actual
  CS2 script that populates the client's display-name state), 'sendClientScript(2498, "i11", 1, 0, 0)',
  '**Config.HAS_DISPLAY_NAME.set(player, 1)**' (varbit 8199 -> resolves to its parent varp via
  'io.dm.cache.Varpbit', the SAME mechanism that already worked on the legacy 184 client),
  'sendClientScript(828, "i", 1)', and two 'sendClientScript(233, ...)' calls.
- 'RsProt.java's old 'doLogin()' called 'player.start()' at what is now line ~262 — BEFORE
  'DmLogin.INSTANCE.accept(...)' had created the RSProt 'Session'. 'PacketSender.queueRsprot()'
  (PacketSender.java:60) returns 'false' with no session, and every send method then falls through to
  the legacy 'OutBuffer'/'write()' path, which ALSO no-ops because RSProt players have a null Netty
  channel (PacketSender.java:42-48). Net effect: the ENTIRE one-shot burst above — including the
  '423' clientscript that sets the display name — was silently dropped for every RSProt login. Only
  varp/varbit writes made via 'Config.set()' survived even partially, because those go through
  'Player.updateVarp()' (dirty-tracking, Player.java:752) and get re-flushed every tick by
  'Player.sendVarps()' once the session exists — which is exactly why the earlier "toggle varp 1055"
  attempt visibly reached the client (it's dirty-tracked) yet still didn't clear the gate: **1055 was
  just the wrong number** (an unverified guess — 'Config.DISPLAY_NAME = varp(1055, true)' in
  Config.java is not a real cache-verified mapping), while the ACTUAL mechanism ('sendClientScript(423,
  "s", name)', an immediate non-dirty-tracked send) never reached the client at all.
- **Fix applied in 'DMS/src/main/java/io/dm/network/rsprot/RsProt.java' ('doLogin()'):**
  1. Removed the early 'player.start()' call (was right after 'player.newPlayer = false;') and the
     ineffective 'io.dm.model.inter.utils.Config.DISPLAY_NAME.set(player, 1)' varp-1055 hack alongside it.
  2. Re-inserted 'player.start()' AFTER the session-null check, 'RebuildLogin', 'setBuildAreas',
     'syncAppearance', and 'openFrame(s)' — i.e. after the RSProt session AND the game frame both
     exist, so 'queueRsprot()' actually queues every packet in the burst instead of dropping it.
  3. Left 'Config.HAS_DISPLAY_NAME' (varbit 8199) as the trusted, cache-verified flag — it was never
     the problem, it just needed its sibling clientscript (423) to actually arrive too.
- **Side benefit:** this also fixes the welcome message, 'LoginListener.executeAll()' UI, pet spawn,
  and daily-reset messages for RSProt players, which were equally being silently dropped by the same
  bug (all called from inside 'Player.start()').
- **Status: code-complete, NOT yet compiled or live-client-tested** (a compile check was in progress
  when this session ended). Next step before trusting this fixed: '(cd DeadMen-RSProt &&
  ./gradlew :DMS:compileJava)', then boot + RSProx login and confirm the "You must set a name..."
  overlay is gone and '::commands'/public chat work.

## Milestone 4 Fix (2026-07-07): Entity & Interface Interaction Wiring
- **Root cause:** 'RsProt.java's Consumer Registry (Phase E) only ever wired four incoming message
  types — 'MoveGameClick'/'MoveMinimapClick' (movement), 'ClientCheat' (::commands), and
  'MessagePublic' (chat). Every other decoded 'IncomingGameMessage' — every object, NPC, ground-item,
  and player click, every inventory/equipment/bank/interface button, and every item-on-X combination
  — fell through to 'DmIncomingPackets.registerNoOpsExcept's accept-and-drop no-op. The packet reached
  the server (so the client never desynced or errored), but no game logic ever ran: clicking anything
  in the world or on any interface was silently swallowed.
- **Fix applied in 'RsProt.java' ('start()'):** registered 11 additional real listeners, each a thin
  bridge from an RSProt-decoded message straight into the existing legacy Kronos handler under
  'io.dm.network.incoming.handlers.*' — no new gameplay logic was written; those handlers already
  fully implement this behaviour for the legacy 184 protocol (and still serve AI bots via that same
  path), they simply weren't reachable from RSProt-connected clients yet:
  - 'OpLoc' (object clicks, options 1-5) -> 'ObjectActionHandler.handleAction'
  - 'OpNpc' (NPC clicks, options 1-5) -> 'NPCActionHandler.handleAction'
  - 'OpObj' (ground-item clicks, options 1-5) -> 'GroundItemActionHandler.handleAction'
  - 'OpPlayer' (player clicks, options 1-8) -> 'PlayerActionHandler.handleAction'
  - 'If3Button' (every inventory/interface/equipment component click, options 1-10) ->
    'ActionButtonHandler.handleAction'
  - 'OpLocT'/'OpObjT'/'OpNpcT'/'OpPlayerT' (item- or spell-used-on-object/ground-item/npc/player) ->
    'InterfaceOnObjectHandler'/'InterfaceOnGroundItemHandler'/'InterfaceOnEntityHandler'
  - 'IfButtonT' (item-on-item, e.g. combining two inventory items) ->
    'InterfaceOnInterfaceHandler.handleAction'
  - 'IfButtonD' (interface drag, e.g. reordering inventory slots) -> 'InterfaceDragHandler.handleDrag'
- **Equip / unequip confirmed end-to-end, not just plumbed:** traced 'If3Button' all the way through
  'ActionButtonHandler.handleAction' -> 'InterfaceHandler.getAction(player, interfaceId, childId)' to
  the actual per-interface handlers. Interface 149 (Inventory) child 0's 'handleClick' is
  'TabInventory.click', which for `option == def.equipOption` (option 1 for ordinary gear) calls
  'player.getEquipment().equip(item)'. Interface 387 (Equipment) children 6-16 (one per worn slot) are
  'TabEquipment's 'itemAction', which for `option == 1` calls 'player.getEquipment().unequip(item)'.
  Both are reached automatically once 'If3Button' is wired — no separate equip/unequip-specific code
  was needed, only the dispatch path itself.
- **Why the plumbing "just fit":** decompiled RSProt's 'CombinedId' value class (bytecode, since only
  'osrs-228-model' ships sources — 'CombinedId' itself lives in the base 'protocol' artifact) and
  confirmed `combinedId = ((interfaceId and 0xffff) shl 16) or (componentId and 0xffff)`, with 0xffff
  ("no value") normalized to -1 on the way out — bit-for-bit the same packed format and sentinel
  convention as the legacy `interfaceHash` parameter every 'ActionButtonHandler'/'InterfaceHandler'/
  'InterfaceOn*Handler' method already takes. So 'msg.getCombinedId()' (or '.getSelectedCombinedId()'/
  '.getTargetCombinedId()' on the *T/'IfButtonD'/'IfButtonT' variants) drops straight into those
  existing parameters with no translation code required.
- **Visibility widened on 8 legacy handler methods, behaviour untouched:** 'NPCActionHandler',
  'PlayerActionHandler', 'GroundItemActionHandler', 'InterfaceOnObjectHandler',
  'InterfaceOnGroundItemHandler', 'InterfaceOnEntityHandler', 'InterfaceOnInterfaceHandler', and
  'InterfaceDragHandler' each kept their real per-option logic in a 'private' (one 'protected') static
  method, reachable only via their own 'handle(Player, InBuffer, int)' entry point in the same package.
  Widened each to 'public static' (pure visibility change, no logic touched) so 'RsProt.java' — in a
  different package — can call them directly with RSProt's already-decoded fields.
  'PlayerActionHandler's private 4-arg 'handle' was additionally renamed to 'handleAction' (its two
  internal call sites updated to match) purely so all four entity-action handlers
  (Object/NPC/Player/GroundItem) share one consistent public entry-point name.
- **isLocked()/resetActions() guard duplicated, not moved, for four of the eight:** 'ObjectAction-',
  'NPCAction-', 'GroundItemAction-', and 'PlayerActionHandler' each apply
  `if(player.isLocked()) return; player.resetActions(true, true, true);` inside their
  'handle(Player, InBuffer, int)' entry point, BEFORE calling into the now-public 'handleAction' this
  milestone bridges into directly — so calling 'handleAction' straight from RSProt would have skipped
  that guard entirely (RSProt players could then fire object/npc/player/ground-item actions while
  stunned/busy/mid-dialogue, or stack actions without clearing the previous one). Rather than move the
  guard into 'handleAction' itself — which would also strip it from those classes' own inline
  'option == 6' (examine) branch, changing existing legacy-184/AI-bot behaviour — each new
  'RsProt.java' bridge method ('onObjectAction'/'onNpcAction'/'onGroundItemAction'/'onPlayerAction')
  duplicates the same two-line guard before calling 'handleAction', leaving the legacy entry points
  completely untouched. The other four handlers ('ActionButtonHandler', 'InterfaceOnGroundItem-'/
  'InterfaceOnObject-'/'InterfaceOnEntity-'/'InterfaceOnInterfaceHandler', and 'InterfaceDragHandler')
  needed no duplicated guard: the first never gated button clicks behind 'isLocked' in the legacy path
  either, and the rest already carry their own 'isLocked()' check *inside* the shared 'handleAction'/
  'handleDrag' method being called, so calling them directly preserves the exact existing guard.
- **Startup-crash trap avoided:** decompiled 'GameMessageConsumerRepositoryBuilder.addListener'
  (bytecode) and confirmed it throws 'IllegalArgumentException' if a message class is registered
  twice. 'DmIncomingPackets.registerNoOpsExcept' registers a no-op for every rev-228 incoming class
  NOT in its caller-supplied exclusion set — so all 11 newly-wired classes had to be added to that
  'java.util.Set.of(...)' alongside the pre-existing four (movement/chat/commands), or the no-op
  registration pass would collide with the real listener and crash the server on boot before ever
  accepting a connection.
- **Scope note:** the three "examine" variants ('OpLoc6'/'OpNpc6'/'OpObj6', the option-6 click on
  objects/NPCs/ground-items) were deliberately left on the existing no-op path — outside the requested
  options-1-through-5 scope, and the legacy handlers' own option-6 branches are debug-only today (no
  player-visible examine text is sent even on the legacy 184 client), so nothing user-visible regresses.
- **Status (2026-07-07): code-complete, compiles clean.** Live-testing began 2026-07-08 — see
  "Milestone 4 Fix — Live Testing Round 1" below for what was found and what's still open. Do not
  treat this milestone as done; several bugs were found once a real client actually clicked things.

## Milestone 4 Fix — Live Testing Round 1 (2026-07-08)
- **First live-test pass reported broken:** wield, drop, inventory limited to visually one item
  (spawning a new item overwrote the previous one), dragging items, and clicking objects moved the
  player but never triggered the object's action. Two real bugs found and fixed; a third fix then
  exposed a fourth. Equip/drop/drag and the bank interface are **still broken** after all of this —
  see the end of this section for current status and next steps.
- **Bug 1 — login never registered the fixed-frame panes as "visible."** 'RsProt.java's
  'openFrame(Session)' queued raw 'IfOpenSub' messages directly (`s.queue(new IfOpenSub(...))`)
  instead of calling 'PacketSender.sendInterface(...)'. That matters because 'sendInterface' does two
  things, not one: it sends the packet *and* calls 'player.setVisibleInterface(interfaceId, parentId,
  childId)' — the bookkeeping 'InterfaceHandler.getAction' checks (via 'isVisibleInterface') before
  running any click handler. Bypassing it meant every fixed-frame pane (inventory 149, equipment 387,
  prayer 541, etc.) rendered correctly on screen but was permanently "not visible" server-side, so
  every click on any of them silently no-opped — explaining wield/drop/drag/interfaces uniformly.
  **Fix:** changed 'openFrame' to take the 'Player' and call
  'player.getPacketSender().sendGameFrame(FIXED_TOP_LEVEL_INTERFACE)' +
  '.sendInterface(pane[0], FIXED_TOP_LEVEL_INTERFACE, pane[1], 1)' per pane, reusing the same
  already-ported, already-correct methods the rest of the game uses to open interfaces (bank, shops,
  etc.), instead of hand-building RSProt messages a second time.
- **Bug 2 — that fix immediately crashed login with an "Index 80 out of bounds for length 80"
  'ArrayIndexOutOfBoundsException' in 'Player.setVisibleInterface'.** Root cause: 'setVisibleInterface'
  sizes its 'visibleInterfaceIds[parentId]' bookkeeping array from 'InterfaceDef.COUNTS[parentId]' —
  and 'InterfaceDef.COUNTS' is loaded from `Server.fileStore.get(3)`, the **legacy** (older-revision)
  cache, per the existing "JS5 cache is a separate FileStore" note above. The legacy cache reports
  interface 548 (the game frame) as having 80 children. The real 228 client's interface 548 has more —

## Protocol & Cache Dump Logging (2026-07-08)
- **Added a permanent, always-on replacement for the temporary '[BUTTON]'/'[DRAG]'/'[INV-CLICK]' console
  diagnostics used throughout the Milestone 4 sections above.** Those were always meant to come out
  "once root-caused and confirmed" (see Round 2's "Diagnostic logging left in place, deliberately" note)
  but were still open pending live re-testing. Instead of stripping them with nothing in their place,
  they're replaced with a permanent, file-based logger so every future live-test session leaves a
  durable record on disk instead of console output that scrolls away.
- **'io.dm.network.logging.NetworkLogger'** (new file) appends one timestamped line per incoming
  interaction packet to 'PROTOCOL_DUMP.txt' (project root — same relative-path convention as
  'RsaKeys'/'server-data/rsa.properties', so it lands next to 'server.properties'). Each line records
  player / packet name / interfaceId / componentId / option / slot / item-or-target-id, plus a free-form
  "extra" segment for packet-specific raw data (world x/z for entity clicks, the second target for
  item-on-item). Also exposes 'interfaceIdFromCombined'/'componentIdFromCombined', unpacking RSProt's
  combined id ('(interfaceId shl 16) or (componentId and 0xffff)', the exact formula this file's own
  "Why the plumbing 'just fit'" note documents) for the message types that only expose the packed form.
- **Wired into all 11 of 'RsProt.java's incoming interaction bridges** — the exact set Milestone 4 wired
  up ('onObjectAction'/'onNpcAction'/'onGroundItemAction'/'onPlayerAction'/'onButton'/'onItemOnObject'/
  'onItemOnGroundItem'/'onItemOnNpc'/'onItemOnPlayer'/'onItemOnItem'/'onInterfaceDrag'). Each now logs
  the packet's raw decoded fields as the very first thing it does, before any 'isLocked'/dispatch logic
  runs, so the dump reflects everything the client actually sent, not just what the server acted on.
  'onButton'/'onInterfaceDrag's old '[BUTTON]'/'[DRAG]' TEMP prints are gone, replaced by this same call.
- **'io.dm.cache.CacheInterfaceDumper'** (new file) runs once at startup, right after
  'InterfaceDef.load()' in 'Server.java' (same place/dependency order — needs 'Server.fileStore',
  'ScriptDef', and 'Varpbit'/'Varp' already loaded). Iterates every interface group in index 3 (the same
  archive 'InterfaceDef' already reads) via this repo's own 'FileStore'/'IndexFile' classes and writes
  each group's id, total child component count, and any scripts/varp/varbit configs
  'InterfaceDef.getScripts()' can resolve for it, to 'CACHE_INTERFACE_DUMP.txt' (project root,
  overwritten fresh each boot — unlike 'PROTOCOL_DUMP.txt', which accumulates across sessions since it's
  a click-session log, not a cache snapshot). Every per-interface step (component count, then
  scripts/configs) is individually try-caught, and the whole 'dump()' body is wrapped again at the
  outermost level, so a corrupt or missing archive entry can only ever produce an "ERROR" line for that
  one interface — it cannot abort the dump or block server boot.
- **Removed the temp diagnostics this replaces**, now that a permanent equivalent is in place:
  'RsProt.java's '[BUTTON]'/'[DRAG]' prints in 'onButton'/'onInterfaceDrag', and 'TabInventory.java's
  '[INV-CLICK]' prints (plus their now-stale surrounding comment) at 'click()'s two silent-return
  branches. Note: 'ActionButtonHandler.handleAction' and 'InterfaceDragHandler.handleDrag' still have
  their own '[BUTTON] resolved ...'/'[DRAG] resolved ...' prints (the "what the dispatcher resolved this
  to" half of the same original diagnostic pair) — intentionally left as-is, out of scope for this pass.
- **Status: infrastructure only, not a behavioural fix.** This doesn't change equip/drop/drag/bank
  behaviour — it gives whoever picks up Milestone 4's still-open items (equip/drop root cause, bank
  rendering) a permanent, greppable record of every click plus the real cache's interface shapes to
  check hypotheses against, instead of re-deriving it by hand or relying on console scrollback.
