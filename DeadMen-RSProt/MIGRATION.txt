# Dead-Men → RSProt Migration Blueprint & Roadmap (Revision 228)
Goal: Replace legacy Kronos Netty network stack with net.rsprot (rev 228 API) and transition server to modern OSRS protocol.

## Module Architecture & Seam Separation
- ':dm-net' Module: Self-contained Kotlin module wrapping RSProt and Netty. Completely isolated from the game model.
- Injection Seams: Implemented in ':DMS' and passed into ':dm-net' via functional lambdas:
  * FilestoreCacheProvider: Feeds raw fileStore bytes over two lambdas:
    val cache = FilestoreCacheProvider(
        rawGroup = { archive, group -> fileStore.get(archive).getArchiveData(group) },
        huffmanTable = { fileStore.getDecompressed(10, "huffman") }
    )
  * DmLoginService: Handles authentication, save deserialization, and game-thread loop registration.
  * Consumer Registries: Binds RSProt IncomingGameMessage listener streams directly to engine handlers via 'NetworkBootstrap.start':
    builder.addListener(If3ButtonClickEvent::class.java) { player, msg -> ActionButtonHandler(...) }
    builder.addListener(MoveGameClick::class.java)       { player, msg -> WalkHandler(...) }

## Remaining Technical Milestones

### Milestone 1: Phase D Zone Payloads (Ground Items, Objects, Projectiles) — [x] CODE COMPLETE (2026-07-07), pending live-client verification
- Legacy Problem: Methods like 'sendGraphics', 'sendCreateObject', 'sendRemoveObject', 'sendGroundItem', 'sendProjectile', and 'sendAreaSound' drop for RSProt connections.
- Migration Path: Wrap these local coordinates and payloads inside RSProt's structural 'UpdateZonePartialEnclosed' envelope.
- Implementation: All six methods ported in 'network/PacketSender.java' via a new 'queueZonePayload(x, y, level, ZoneProt)' helper, which builds the appropriate payload ('ObjAdd'/'LocAddChangeV2'/'LocDel'/'MapAnim'/'MapProjAnim'/'SoundArea'), encodes it with 'DesktopUpdateZonePartialEnclosedEncoder.Companion.buildCache(...)', and queues the resulting 'UpdateZonePartialEnclosed' on the player's session.
- Gradle Fix Required: 'dm-net/build.gradle' needed explicit 'api' dependencies added on 'osrs-228-desktop' and 'osrs-228-internal' — RSProt's published Gradle metadata only exposes those two modules on the runtime classpath by default, not compile, and the zone-payload buffer builder lives in 'osrs-228-desktop'.
- Correction During Implementation: an early draft targeted RSProt rev 239's 'MapProjAnimV2' by mistake; corrected to rev 228's actual 'MapProjAnim' (different field layout — relative deltaX/deltaZ, not absolute end-coordinates). Full rationale in HANDOFF.txt under "Milestone 1 Fix".
- Live-Testing Round 1 (2026-07-08): ground items spawned via 'ObjAdd' (and by extension every other zone-scoped send, since all six share the same helper) produced no server error but rendered nothing on the client. Root cause: 'queueZonePayload' built its 'UpdateZonePartialEnclosed' wrapper with the zone's *shifted/divided* coordinate form (`x >> 3`), but RSProt's own KDoc for 'UpdateZonePartialEnclosed'/'UpdateZoneFullFollows'/'UpdateZonePartialFollows' (read directly from the 'osrs-228-model' sources jar) is explicit that this packet family's zoneX/zoneZ are the zone's south-western corner in *absolute tile coordinates* (worked example in the doc itself: x=50 → expected 48, not 6) — a deliberately different convention from 'RebuildNormal'/'updateBuildArea's same-named parameters, which genuinely do use the shifted form. Every zone update was silently targeting the wrong zone. Fixed by changing `x >> 3, y >> 3` to `x & ~0x7, y & ~0x7` in 'PacketSender.queueZonePayload' — the single shared helper behind all six sends, so this should resolve ground items, object add/remove, projectiles, graphics and area sounds together. Full rationale in HANDOFF.txt under "Milestone 4 Fix — Live Testing Round 3" (filed there since that's the live-testing session that found it, though the fix lives in this milestone's own code).
- Remaining: live-client verification via RSProx of the coordinate fix above — confirm ground items, objects, projectiles, graphics, and area sounds all render/play at the *correct tile* now. 'sendProjectile' (curve→angle, something→progress) and 'sendAreaSound' (type→loops, distance→range/dropOffRange) still separately used best-effort positional field mapping with no exact legacy-name match, so these two remain the most likely to need further visual/audio tuning even once the coordinate fix is confirmed.

### Milestone 2: Map Engine Update Masks to RSProt Extended Info — [x] CODE COMPLETE (2026-07-07), pending live-client verification
- Legacy Problem: Player character animations, graphics, hitpoints, spot-anims, face-entity, and forced movement updates drive through 'PlayerUpdater.process()' and legacy 184 bitpacking.
- Migration Path: Port the 12 mask structures in 'model/entity/shared/masks/' to execute setters on the 'PlayerAvatarExtendedInfo' object.
- Execution Order: 'RsProt.pushMaskUpdates(Player)' runs as a new step 0 at the top of 'RsProt.driveUpdate()', once per online RSProt player, before step 3's 'playerInfoProtocol.update()' gathers each avatar's flagged extended-info blocks into that cycle's snapshot.
- Implementation: 11 of the 12 mask classes map onto 'PlayerAvatarExtendedInfo' setters (Animation->setSequence, Graphics->setSpotAnim, Hits->addHitMark+addHeadBar, Chat->setChat, EntityDirectionUpdate/face-entity->setFacePathingEntity, MapDirectionUpdate/face-angle->setFaceAngle, ForceText->setSay, ForceMovement->setExactMove, MovementMode->setMoveSpeed, TeleportMode->setTempMoveSpeed, Appearance->re-invokes the existing login-time 'syncAppearance()' whenever dirty). The 12th class, 'TransformUpdate', is NPC-only (never instantiated on 'Player') and is out of scope here — bridging it belongs to a future NPC-info milestone alongside 'NpcAvatarExtendedInfo'.
- Correction During Implementation: caught a "replays forever" bug before it shipped — 'Entity.resetUpdates()' only clears a mask once 'isSent()' is true, and only the legacy 'PlayerUpdater.writeMasks()' (never called for RSProt players) used to set that flag, so every consumed mask now gets explicitly marked 'setSent(true)' inside 'pushMaskUpdates()' itself, or its animation/graphic/hitsplat/chat would have re-fired every tick forever instead of once. 'ChatUpdate' also discarded its plaintext message after Huffman-encoding it for the legacy wire format, leaving nothing for RSProt's self-encoding 'setChat()' to consume — fixed by retaining the case-fixed string alongside the existing encoded bytes. 'EntityDirectionUpdate' (face-entity) needed two further fixes, not a passthrough: RSProt's player-index offset (+0x10000) differs from the legacy client-index offset (+32768), and the legacy code's intentional 2-cycle delayed-revert (a 184 client quirk) would have added a visible, unnecessary lag to un-facing on RSProt. All detailed in HANDOFF.txt under "Milestone 2 Fix".
- Remaining: hit-source tinting is a best-effort gap (hitmarks/hp-bar push with no attacker index, since the legacy 'Splat' never kept one — damage numbers and the hp bar still render correctly for everyone). Live-client verification via RSProx — confirm animations, spot-anims, hitsplats/hp bar, forced movement, face-entity/face-angle, and force-text/chat bubbles all render correctly on a real character. Full rationale in HANDOFF.txt under "Milestone 2 Fix".

### Milestone 3: Unlocking the Chatbox Input Gate — [x] CODE FIX APPLIED (2026-07-07), pending live-client verification
- Original Problem: Client input is hard-blocked by a "You must set a name before you can chat" overlay. Public chat ('MessagePublic') and commands ('ClientCheat') drop.
- Root Cause Found: Not a wrong Varbit/Varp. 'Player.start()' fires the one-shot login packet burst that includes 'sendClientScript(423, "s", name)' (sets the client's own display-name state) and 'Config.HAS_DISPLAY_NAME.set(...)' (varbit 8199, the mechanism that already worked pre-migration on the legacy 184 client). 'RsProt.java' was calling 'player.start()' BEFORE the RSProt 'Session' existed, so 'PacketSender.queueRsprot()' silently no-op'd the entire burst every login — the earlier "toggle varp 1055" attempt only proved that dirty-tracked varp writes eventually reach the client; 1055 itself was just the wrong (unverified) id, and it was masking the real bug (script 423 never arriving at all).
- Fix Applied: In 'RsProt.java doLogin()', moved 'player.start()' to run AFTER 'DmLogin.INSTANCE.accept(...)' + 'RebuildLogin' + 'syncAppearance' + 'openFrame(s)' (i.e. after the session and game frame both exist), and removed the ineffective 'Config.DISPLAY_NAME' (varp 1055) hack. Full rationale logged in HANDOFF.txt under "Milestone 3 Fix".
- Remaining: compile ('./gradlew :DMS:compileJava') and confirm live via RSProx login that the overlay clears and '::commands'/public chat work end-to-end.
- Interim Workaround (still in place): temporary starter kit injected inside 'RsProt.doLogin' so items, equipment look, and bank container logic can be live-tested without chat interactions.

### Milestone 4: Entity & Interface Interactions — [~] PARTIALLY WORKING (2026-07-08), live-tested, under active investigation
- Legacy Problem: Clicking Objects, NPCs, ground Items, Players, or any interface component (inventory, equipment, banking, etc.) did nothing for RSProt connections. 'RsProt.java's Consumer Registry (Phase E) only wired movement/chat/commands; every other decoded 'IncomingGameMessage' fell through to 'DmIncomingPackets.registerNoOpsExcept's accept-and-drop no-op, so the packet reached the server but no game logic ever ran.
- Migration Path: Register real listeners for the remaining "primary interaction" packet family in 'RsProt.java's 'start()' builder (the same Consumer Registry pattern Phase E proved for 'MoveGameClick') and bridge each straight into its existing legacy Kronos handler under 'io.dm.network.incoming.handlers.*' — no new gameplay logic was written; those handlers already fully implement object/npc/item/interface behaviour for the legacy 184 protocol (and still serve AI bots via that path), they just weren't reachable from RSProt clients.
- Implementation: 11 new listeners in 'RsProt.java': 'OpLoc'/'OpNpc'/'OpObj' (options 1-5) -> 'ObjectActionHandler'/'NPCActionHandler'/'GroundItemActionHandler'; 'OpPlayer' (options 1-8) -> 'PlayerActionHandler'; 'If3Button' (options 1-10, covers every inventory/interface/equipment click) -> 'ActionButtonHandler'; 'OpLocT'/'OpObjT'/'OpNpcT'/'OpPlayerT' (item- or spell-used-on-X) -> 'InterfaceOnObjectHandler'/'InterfaceOnGroundItemHandler'/'InterfaceOnEntityHandler'; 'IfButtonT' (item-on-item) -> 'InterfaceOnInterfaceHandler'; 'IfButtonD' (interface drag, e.g. reordering inventory slots) -> 'InterfaceDragHandler'.
- Correction During Implementation: eight legacy handler methods ('NPCActionHandler', 'PlayerActionHandler', 'GroundItemActionHandler', 'InterfaceOnObjectHandler', 'InterfaceOnGroundItemHandler', 'InterfaceOnEntityHandler', 'InterfaceOnInterfaceHandler', 'InterfaceDragHandler') were 'private'/'protected', reachable only from their own opcode-table entry point in the same package — widened to 'public static' (and 'PlayerActionHandler's private 4-arg 'handle' renamed to 'handleAction' to match its three siblings) so 'RsProt.java' can call them directly. The 'isLocked()'/'resetActions()' guard on the four direct entity-action handlers lives in their legacy 'handle(Player, InBuffer, int)' entry point, not in the 'handleAction' method these bridges call — duplicated in each 'RsProt.java' bridge rather than moved, so the untouched legacy-184/AI-bot path keeps its exact existing behaviour. Also confirmed via decompiled bytecode that RSProt's 'GameMessageConsumerRepositoryBuilder.addListener' throws 'IllegalArgumentException' on a duplicate class registration, so every newly-wired packet class had to be added to the 'registerNoOpsExcept' exclusion set or the server would crash on boot. Full rationale in HANDOFF.txt under "Milestone 4 Fix".
- Live-Testing Round 1 (2026-07-08): found 'RsProt.java's login-time 'openFrame()' queued raw 'IfOpenSub' messages directly instead of going through 'PacketSender.sendInterface()', skipping the 'Player.setVisibleInterface(...)' bookkeeping that 'InterfaceHandler.getAction' checks on every click — every fixed-frame pane (inventory, equipment, etc.) rendered but was permanently "not visible" server-side. Fixing that exposed a second, previously-latent bug: 'Player.setVisibleInterface's bookkeeping arrays are sized from the LEGACY cache's 'InterfaceDef.COUNTS' (interface 548 = 80 children there), but the real 228 client's interface 548 has more (fixed-frame panes go up to slot 93) — crashed login with an 'ArrayIndexOutOfBoundsException' the moment a pane at index >= 80 was opened. Fixed by making 'setVisibleInterface'/'removeVisibleInterface'/'isVisibleInterface'/'moveVisibleInterface' grow their arrays on demand instead of trusting the legacy count. Also found 'PacketSender.updateItems()' (partial inventory sync, 'UpdateInvPartial') was packing item data with the 2-arg 'InventoryObject.pack(id, count)', which silently packs slot 0 — RSProt reads the target slot back out of the packed value itself for partial updates (unlike full syncs, where position is the slot), so every changed item was telling the client "slot 0 changed," visually stomping whatever was there. Fixed with the 3-arg 'pack(slot, id, count)'. Full rationale in HANDOFF.txt under "Milestone 4 Fix".
- Confirmed working live after the above fixes: login (no crash), object/NPC/ground-item clicks and movement, and inventory item display (new items land in their own slot instead of all colliding on slot 0).
- Still broken live (as of Round 1): equipping items, dropping items, and dragging items within the inventory (all three route through interface 149's registered 'TabInventory' action) — clicks don't appear to take effect. Opening the bank sends its full expected packet sequence server-side (login-frame 'IfOpenSub' + all 'sendAccessMask'/'sendString' calls, no exceptions) but no bank interface appears on the client.

## Diagnostic Infrastructure (2026-07-08)
- Added permanent, file-based protocol + cache logging, replacing the ad hoc '[BUTTON]'/'[DRAG]'/
  '[INV-CLICK]' console diagnostics referenced throughout Milestone 4 above. Global, file-based protocol
  and cache logging is now active across the entire protocol surface.
- 'io.dm.network.logging.NetworkLogger': appends every incoming interaction packet (all 11 listeners
  'RsProt.java' registers per Milestone 4 — object/npc/player/ground-item clicks, interface button
  clicks, item-on-X combinations, interface drag) to 'PROTOCOL_DUMP.txt' (project root) with a timestamp
  and the packet's raw decoded fields (interface/component/option/slot/item-or-target id).
- 'io.dm.cache.CacheInterfaceDumper': runs once at server startup (after 'InterfaceDef.load()' in
  'Server.java'), walks every interface group in the loaded cache via this repo's own 'FileStore'/
  'IndexFile' classes, and writes each group's id/component count/resolved scripts+configs to
  'CACHE_INTERFACE_DUMP.txt' (project root, regenerated fresh each boot). Fully try-caught per interface
  so a corrupt archive entry can't block boot.
- This is tooling, not a behavioural fix — it gives the still-open Milestone 4 items (equip/drop/drag
  root cause, bank rendering) a durable, greppable record of live click sessions and the real cache's
  interface shapes to check hypotheses against, instead of console scrollback. Full rationale in
  HANDOFF.txt under "Protocol & Cache Dump Logging".
