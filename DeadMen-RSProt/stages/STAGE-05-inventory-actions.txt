### Bug 2 — real root cause: 228's op-numbering isn't "index+1" (FIXED)

### Opcode desync — FULLY CLOSED
Fixed all 8 opcodes `ItemDef.decode(InBuffer,int)` didn't recognize, in two passes (fixing the
first batch unmasked more sitting behind them in the byte stream): `3` (item description/examine

`42` (shift-click drop option index byte — unused), `43` (a VARIABLE-LENGTH sub-options block, not
a fixed field — one group-id byte then a 0-terminated sequence of (subopId byte, text string)
pairs; had to replicate this loop structure exactly or it would desync just as badly as not
handling the opcode at all). Sourced from AlterRSPS's actively-maintained `ItemDecoder.kt`
(`plugins/filestore/.../definition/decoder/ItemDecoder.kt` on github.com/AlterRSPS/Alter — fetched

guidance if picking this up fresh) — the same source also confirmed opcode `42`'s width/purpose

matching code for that one opcode. Result: `ITEM_OPTION_DUMP.txt`'s "Unknown opcodes" section is
now EMPTY (0 across all 24604 items) — the byte-parser is provably exhaustive against the real
Cache228 archive on disk. `ItemDef.isKnownOpcode(int)` updated to match.

### ItemOptionDumper performance bug (15+ minutes → seconds) — FIXED
Unrelated to opcodes, found while iterating on the above: `IndexFile.getFile()`
(`kronos-api/.../IndexFile.java:103-111`) has a "consume-and-null-on-read" cache — the FIRST call
to `getFile(10, anyId)` decompresses the ENTIRE ~24,604-item Cache228 archive in one shot, but
immediately nulls the specific slot it returns. `ItemOptionDumper` was calling `getFile(10, id)`
TWICE per item (once inside `Cache228ItemDefs.get()`, once again directly for the unknown-opcode
check) — so the second call for that same id always found its slot already null and re-triggered a
FULL re-decompression of the entire archive from scratch. ~24,604 redundant full-archive
decompressions is what actually caused the 15+ minute runtime, not raw item count. Fixed by reading
each item's raw bytes exactly once and reusing them for both the decode and the opcode-scan — dump
now completes in a few seconds. NOT a threading problem, and threading would have been actively
risky to add on top: `IndexFile` has a `static` shared read buffer
(`private static final byte[] readCachedBuffer`) across ALL `IndexFile` instances, so concurrent
reads against a DIFFERENT index while this runs could corrupt each other — likely the actual cause
of the "Invalid Sector (0): 330638 (255,16)" garbage seen in a boot log this round, from unrelated
concurrent cache loading during normal startup. That static-buffer issue is real but out of scope
for this stage — noted here for whoever eventually touches `IndexFile` concurrency.

### Built a JS5 cache write path (previously read-only) and used it to add "Use" to 30,529 items
This project's `kronos-api` cache classes (`FileStore`/`IndexFile`/`Archive`/`ReferenceTable`) were
read-only. Built a temporary standalone tool (`TempCacheWriter.java`, deleted after use — not part of
the deliverable) that empirically reverse-engineered the write side directly against the real
Cache228 files (not guessed, not assumed from generic OSRS cache docs) and confirmed every fact below
by testing against a disposable scratch copy before ever touching the real cache:
- **Container format**: `[1-byte compression][4-byte len1][4-byte len2 if compressed][payload]
  [2-byte version — DATA GROUPS ONLY, e.g. item defs; reference tables do NOT have this]`. Confirmed
  empirically: item archive 2/10's actual last 2 bytes (`06 06` = 1542) bit-for-bit equal the
  reference table's declared revision for group 10.
- **Reference-table crc convention**: `crc32(that group's full container MINUS the trailing 2-byte
  version)`. Confirmed by recomputing and matching the stored value exactly.
- **compression=1 is bzip2** (this codebase has a decoder only, `io.dm.api.filestore.utility.BZIP
  .method3143` — public, reused read-only here — but no encoder). **Anything this tool WRITES uses
  compression=2 (gzip)**, via `GZIPOutputStream`/`GZIPInputStream` (not hand-rolled Deflater+trailer
  bytes) — sidesteps needing a bzip2 encoder entirely, and is equally valid per the format.
- **`IndexFile`'s constructor hardcodes `maxLength=1_000_000`** for every regular index
  (`FileStore.java`) — an uncompressed container (~2.26MB decompressed) exceeds this and
  `getArchiveData` legitimately rejects it as "Invalid Archive Length!", returning null. This is WHY
  compression is mandatory here, not optional — discovered by hitting this exact rejection against
  the real `IndexFile` class before switching from an initial uncompressed attempt to gzip.
- **Multi-file container trailer** (the format `IndexFile.cacheArchiveFiles` already parses): files
  concatenated back-to-back, followed by a delta-encoded per-file-size trailer + a 1-byte chunk
  count. Reused a single chunk (`amtOfLoops=1`) when re-emitting — a valid degenerate case of the
  same format, not a different one. Verified byte-for-byte: decompose then immediately recompose the
  UNMODIFIED real payload and diff against the original — identical, before ever attempting a real
  edit.
- **Sector-chain writing**: always allocates fresh sectors by appending at EOF (padding `dat2` to the
  next 520-byte boundary first, since the real file's last sector is often not padded) — never
  reuses or overwrites existing sectors, so a bug mid-write cannot corrupt anything already in the
  file, only leave harmless trailing garbage.
- **Where "Use" gets inserted per item**: the highest free raw option slot among 0-3 (checked 3 down
  to 0), i.e. closest to Drop — matches real OSRS's documented Wield/Eat/Use/Drop/Examine ordering
  (e.g. whip becomes `[null,Wield,null,Use,Drop]`, godsword becomes
  `[null,Wield,Dismantle,Use,Drop]`), rather than always using slot 0. Items that already contain
  literal "Use" text anywhere (just the 1 pre-existing item, 5606) are skipped entirely, not
  double-added. Items with all 4 slots already occupied are left untouched (113 of them).
- **One item (11169) throws presented as a decode error, not a corruption**: `ItemDef.decode()` has
  a hardcoded `case 11169:` that calls `World.type.getWorldName()` — a live-server-only value, never
  a fact about this item's cache bytes. This standalone tool never boots the full server, so
  `World.type` is null and this throws. Confirmed pre-existing and unrelated to this change by
  running the identical check against the untouched backup — same exception, same item, before any
  write ever happened. Left this ONE item's raw bytes completely untouched rather than guess how the
  hardcoded override would interact with an edit.
- **Validation, in order, before touching the real cache**: (1) decompose/recompose identity on the
  real unmodified payload: byte-for-byte match. (2) Wrote to a disposable scratch copy of the full
  166MB cache, never the real one, until every check below passed. (3) Re-read via a FRESH
  `io.dm.api.filestore.FileStore` (the actual production class, not this tool's own parser) and swept
  every item through the actual production `ItemDef.decodeStandalone` — 30,643 decoded cleanly (the
  1 pre-existing 11169 exception aside), reference table crc/revision matched expectations exactly,
  spot-checked items with existing customs (godsword), no customs (coins, hilt), and other
  known-content items (lobster) all correct and none corrupted.

### "Use" had no way to ever complete an interaction — access mask never granted targeting capability
The human reported two things after Round 6 shipped: (1) "Use" needs its actual action wired up now
that the cache patch put it on every item, and (2) left-clicking an item opens the right-click menu
instead of performing an action directly. Investigated both.

**Root cause of (1), confirmed via primary source, FIXED:** `RsProt.openFrame(Player)` sends the
inventory's access mask (`sendAccessMask(Interface.INVENTORY, 0, 0, 27, 1181694)`) once at login.
That value only ever encoded the ten `ClickOpN` capability bits (bits 1-10) plus drag-reorder (bits
17+20) — it never granted the SEPARATE capability bits that let the client build an item-on-X
"targeting" packet at all. RSProt's own `IfSetEvents.events` field is opaque (confirmed again this
round straight from `IfSetEvents.kt`'s KDoc in the `osrs-228-model` sources jar — RSProt does not
interpret or name these bits), so named ground truth came from AlterRSPS's `InterfaceEvent` enum
(`game-api/src/main/kotlin/org/alter/api/ext/InterfaceEvents.kt` on github.com/AlterRSPS/Alter — same
rev-228 reference this project has already cited for `ItemDecoder.kt`/`InterfaceDestination.kt`,
fetched fresh this round via the GitHub API/raw content, not from memory): `ClickOp1..10 = 1 shl 1`
through `1 shl 10` (confirms bits 1-10 was already right), then six more bits that were never granted:
`UseOnGroundItem = 1 shl 11`, `UseOnNpc = 1 shl 12`, `UseOnObject = 1 shl 13`, `UseOnPlayer = 1 shl
14`, `UseOnInventory = 1 shl 15` (item-on-item), `UseOnComponent = 1 shl 16` (cross-interface
targeting, e.g. an item onto a different interface's component — not granted, out of scope, no
current listener depends on it). Without bits 11-15, the client has permission to let the player
*select* an item via "Use"/a spell (that part only needs `ClickOpN`, already granted) but has NO
permission to ever transmit the follow-up `OpLocT`/`OpObjT`/`OpNpcT`/`OpPlayerT`/`IfButtonT` packet
once the player clicks a target — meaning every one of Milestone 4's "wired but never actually
tested" item-on-X listeners (`onItemOnObject`/`onItemOnGroundItem`/`onItemOnNpc`/`onItemOnPlayer`/
`onItemOnItem` in `RsProt.java`) was structurally unreachable from the moment they were written, for
an entirely different reason than anyone had checked before (everyone assumed "wired but untested"
meant "probably fine, just never watched" — it actually meant "cannot possibly have worked").
**Fix applied**: `RsProt.java`'s `openFrame(Player)`, inventory mask `1181694` → `1245182` (adds bits
11-15, i.e. `+2048+4096+8192+16384+32768 = +63488`). Single-line change, same call site, full
reasoning recorded in a new doc comment directly above it. Equipment's mask (`2046`, worn slots
6-16) was deliberately NOT touched — real OSRS doesn't offer "use item on a worn equipment slot" as

### Item-on-item within the same inventory never worked because it isn't delivered as IfButtonT at all
Human confirmed item-on-object, item-on-npc, and item-on-ground-item all work live after Round 7's
access-mask fix, but item-on-item (combining two items in your own inventory, e.g. Use a tinderbox
then click logs) still did nothing. Root-caused with concrete evidence instead of guessing at another
access-mask bit:

- **`DMS/PROTOCOL_DUMP.txt` (this project's own accumulated live-capture log, going back to
  2026-07-08) contains ZERO `IfButtonT` lines across the ENTIRE migration** — confirmed by grepping
  the whole file, not just this session's activity. Every single time two inventory items were
  targeted at each other (both the human's fresh 2026-07-11 19:27 test — coins onto the whip, then
  the whip onto coins — and an earlier 2026-07-08 21:27 capture of an Armadyl hilt dragged onto a
  blade) the logged packet was `IfButtonD` (the DRAG message), not `IfButtonT` (the "use item, click
  target" message that `RsProt.onItemOnItem`/`InterfaceOnInterfaceHandler`/`TabInventory.onInterface`
  are built to handle). By contrast, `OpLocT`/`OpNpcT`/`OpObjT` (object/npc/ground-item targeting)
  show up correctly for the exact same "select item, click target" user action, just aimed at
  something outside the inventory.
- **Conclusion: the real rev-228 client represents "use an item on another item in the same
  inventory" as a drag event, full stop — never as an `IfButtonT`.** This isn't a mask gap (no amount
  of `UseOnInventory`/`UseOnComponent` tuning would matter, since the client was never going to send
  that message type for this interaction in the first place) and isn't a dispatch bug in
  `InterfaceOnInterfaceHandler`/`TabInventory.onInterface` (that code is fine, just unreachable for
  this specific case — it may still matter for a genuinely different scenario, e.g. using an
  inventory item on a component in a DIFFERENT interface, which nobody has tested). The actual bug is
  in the drag handler: `TabInventory.drag(player, fromSlot, toSlot)` (the method
  `InterfaceDragHandler`/`RsProt.onInterfaceDrag` already correctly routes every `IfButtonD` to)
  unconditionally swapped the two slots' contents — it never checked whether the two items could
  combine at all. Real OSRS's actual drag semantics: if the dragged item and its target combine,
  combine them; otherwise, swap positions as an ordinary reorder. This project's drag handler only
  ever implemented the second half.
- **Fix applied, two files:**
  1. `DMS/src/main/java/io/dm/model/item/actions/ItemItemAction.java` — extracted the existing
     `handleAction`'s match/dispatch logic into a new `tryHandle(Player, Item, Item)` that returns
     `true`/`false` instead of always falling back to `"Nothing interesting happens."`. `handleAction`
     itself is now a two-line wrapper (`if(!tryHandle(...)) player.sendMessage(...)`) — behavior for
     its existing caller (`TabInventory.onInterface`, the still-wired-but-so-far-unobserved `IfButtonT`
     path) is completely unchanged.
  2. `DMS/src/main/java/io/dm/model/inter/handlers/TabInventory.java` — `drag()` now calls
     `ItemItemAction.tryHandle(player, fromItem, toItem)` before performing the swap, only when
     `toItem` is non-null (an empty destination slot is always a plain move, matching existing
     behavior exactly). If a combo is found, `tryHandle` performs it and `drag()` returns immediately
     without touching either slot's contents (the registered `ItemItemAction` is responsible for
     consuming/producing items itself, same as it already is for the `IfButtonT`/Use-then-click path).
     If no combo is found, execution falls through to the exact same swap code that existed before —
     zero behavior change for ordinary inventory reordering. Deliberately used `tryHandle`, not
     `handleAction`, specifically so a plain reorder-drag between two non-combinable items (the
     overwhelmingly common case) doesn't spam "Nothing interesting happens." on every drag.
- **Why `tryHandle` instead of just calling `handleAction` and checking a return value**: `handleAction`
  has no return value and unconditionally messages on a miss — swapping is the correct, silent
  behavior for a miss during a drag (that's just normal inventory reordering), not a "failed
  interaction" that deserves a message. Splitting the message-on-miss behavior out of the shared
  lookup was the minimal change that let both callers keep their own correct behavior.
- **Compiles clean** (`./gradlew :DMS:compileJava`, 2026-07-11). **NOT yet live-tested** — next step is
  the human re-testing exactly the sequence that failed before (Use a combinable pair, or physically
  drag one onto the other, within the inventory) and confirming the combine actually fires. Also worth
  a quick regression check that ordinary reorder-dragging two non-combinable items still just swaps
  silently (no stray messages).
- **Scope note for whoever picks up Stage 08 (item-on-item / drag) next**: this fix lives in
  `TabInventory.drag`, which Stage 08's own file already flagged as a dependency
  (`resolveRawIndex`-adjacent reasoning). The `IfButtonT` path (`onItemOnItem` in `RsProt.java`,
  `InterfaceOnInterfaceHandler`, `TabInventory.onInterface`) is left fully in place, untouched — it
  may still be exercised by a cross-interface "use inventory item on a DIFFERENT interface's
  component" scenario nobody has tested yet (e.g. an item used on a bank/shop slot). Don't assume it's
  fully dead code just because same-inventory combining doesn't use it.
