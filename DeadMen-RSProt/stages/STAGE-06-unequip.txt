## GOAL
Clicking a worn item in the equipment tab (interface 387) unequips it back to inventory.

## SYMPTOM (human-reported 2026-07-08)
"Equipment doesn't work correctly - I can force equip items, and they appear in the correct
place, but I'm unable to unequip things from the player."
(The "appear in the correct place" part means the equipment container, appearance sync, and the
387 pane rendering are all fine — ONLY the click→unequip path is broken.)

## KNOWN STATE (resolved this round — see HANDOFF.txt's "STAGE 06" entry for full detail)
- RESOLVED: the access-mask loop's documented range (was 6..16) never matched TabEquipment.java's
  real registrations (childIds 1, 5, 7, 15-24) — corrected to 15-25. Live evidence (PROTOCOL_DUMP.txt
  clicks landing on childIds outside 6..16 and still dispatching) shows this single-component mask's
  start=-1/end=-1 form doesn't actually gate individual childIds, so this was a documentation fix,
  not a functional unblock.
- RESOLVED: TabEquipment.java's static block assigned `h.actions[24]` twice (RING then AMMO
  overwrote it) — RING never had a working handler, and the real 11th slot (AMMO) belongs at childId
  25, one past interface 387's cache-reported component count (25 total, i.e. valid indices 0-24 —
  confirmed empirically against the real legacy Cache/ folder). Split into actions[24]=RING,
  actions[25]=AMMO, and widened InterfaceHandler's capacity for interface 387 to 26 via a new
  `InterfaceHandler.register(int, int, Consumer)` overload (otherwise registering childId 25 would
  throw ArrayIndexOutOfBoundsException and silently kill TabEquipment's entire static initializer).
- Expected server path when the packet arrives: If3Button → ActionButtonHandler →
  InterfaceHandler.getAction(387, childId 15-25) → TabEquipment.itemAction → option 1 →
  player.getEquipment().unequip(item). Read closely this round and looks structurally correct for
  the 10 slots (15-23) that were already registered before this fix — genuinely unverified live,
  though, since no session ever captured the `[BUTTON] resolved ...` console line for an equipment
  click (only the raw packet). If those still don't unequip after this fix, get that console line
  before guessing further — see the updated TEST SCRIPT below.
