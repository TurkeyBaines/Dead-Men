## GOAL
Clicking an object performs its action when the player arrives: doors open, ladders climb, trees
chop, bank booths open the bank (rendering needs Stage 04).

## SYMPTOM (human-reported 2026-07-08)
"Object actions register, but just like items, nothing actually happens (you move to an object,
but don't interact with it)."
IMPORTANT NUANCE: the click IS received (OpLoc is wired → ObjectActionHandler, confirmed live in
earlier testing) and the player DOES path toward the object. What never happens is the action
executing on arrival. So this is NOT a packet/dispatch bug — it's in the walk-to-then-act
pipeline, or in what the handler does once reached.

## ROUND 1 FINDINGS (2026-07-11) — the full chain, documented for the first time
1. `ObjectActionHandler.handleAction(player, option, objectId, objectX, objectY, ctrlRun)` (called
   from both the legacy `handle()` entry point and directly from `RsProt.onObjectAction`) looks the
   object up via `Tile.getObject(objectId, objectX, objectY, player.getPosition().getZ())`
   (`Tile.java:161-181`), which does an EXACT match on `gameObject.id == id` at that tile — not a
   position-only match. Returns silently (no message, no walk) if not found.
2. If found, it calls `player.getMovement().setCtrlRun(...)` then
   `player.getRouteFinder().routeObject(gameObject, successAction)` where `successAction` is a
   closure that resolves `gameObject.actions[option-1]` (per-instance override) falling back to
   `gameObject.getDef().defaultActions[option-1]` (cache-wide default, populated at boot by ~211
   `ObjectAction.register(...)` call sites across the codebase, e.g. `Door.java`'s static block),
   and either calls `action.handle(player, gameObject)` or sends "Nothing interesting happens."
3. `RouteFinder.routeObject(GameObject, Runnable)` (`RouteFinder.java:211-271`) has TWO paths:
   - Fast path (already adjacent): runs `successAction` if `route.reachable`, else checks
     `gameObject.skipReachCheck` (a per-object override predicate, null for ordinary objects), else
     calls `Movement.outOfReach()` — which sends the player a very visible "I can't reach that!"
     chatbox message + sound (`PlayerMovement.java:128-131`). This message pipeline is confirmed
     working for RSProt players (chat/commands/examine text all work per BASELINE-FINDINGS.txt), so
     if this branch were firing the human should have seen it. Not mentioned in the original
     symptom report — genuinely unknown whether it fired or not, hence the new instrumentation
     rather than assuming either way.
   - Event path (not yet adjacent): starts an `Entity.startEvent(...)` that delays 1 tick at a time
     until `Movement.isAtDestination()`, with a SILENT (`no message`) early return if
     `gameObject.id != id || gameObject.tile == null` at any point (object changed/removed under
     the player's feet) — checked both mid-wait and immediately after arrival. Once truly arrived,
     it re-checks `route.reachable && route.finished(position)` and either fires `successAction`,
     falls back to `skipReachCheck`, or calls the same loud `outOfReach()` as the fast path.
4. `Entity.startEvent()` (`Entity.java:495-498`) calls `stopEvent(true)` (kills the entity's
   currently-`active` event, if any and not persistent) then stashes the new event in `nextEvent`,
   which is only promoted to `activeEvent` on the entity's NEXT `processEvent()` tick
   (`Entity.java:513-522`). `processEvent()` is called unconditionally from `Player.process()`
   (`Player.java:1636-1668`), which `CoreWorker.logic()` calls unconditionally for every online
   player regardless of RSProt/legacy transport (`CoreWorker.java:97-106` — no session/channel
   check anywhere in that call path). Movement stepping (`Movement.process()`) is driven the exact
   same way. This entire chain is 100% shared, RSProt-unaware legacy code, and the same mechanism
   underpins ~211 other `ObjectAction.register` call sites across raids/skilling/wilderness/etc.
   content that presumably worked fine before this migration touched only the network layer.
5. Net effect: there are exactly THREE ways this can end silently (no "I can't reach that!", no
   "Nothing interesting happens.", no world effect) — (a) `gameObject == null` at the very first
   lookup, (b) the `id != id || tile == null` bail inside the event wait-loop or right after it,
   or (c) `successAction` running but resolving `action == null` from BOTH `actions[i]` and
   `getDef().defaultActions[i]` — wait, that last one actually DOES send "Nothing interesting
   happens.", so it is NOT silent; listed here only to be explicit that it's already ruled out as
   a *silent* failure mode, not that it's ruled out as *a* failure mode (the human may simply not
   have mentioned that chat line). All five `[OBJACTION]` print sites added this round map 1:1 onto
   these branches, so the next live test resolves this by direct observation instead of inference.

## ROUND 2 FINDINGS (2026-07-13) — ObjectDef opcode-desync bug, found and fixed without a live client
While preparing to hand this stage back for a fresh live test (per the 2026-07-12 cache-switch
note above), re-examined `ObjectDef.decode(InBuffer,int)` (`DMS/src/main/java/io/dm/cache/
ObjectDef.java`) since Stage 05's HANDOFF note explicitly says "read Stage 05's note if it's done —
its root cause may be yours too." Stage 05's closed "opcode desync" bug for `ItemDef` had the exact
same shape: `decode(InBuffer,int)` has no catch-all `else` branch, so any cache opcode it doesn't
recognize silently consumes zero payload bytes instead of erroring — desyncing every field decoded
afterward for that record. `ObjectDef.decode` has the identical structure and had never been
audited this way.
1. Built `ObjectDef.findFirstUnknownOpcode(byte[])` + `isKnownOpcode(int)`, mirroring `ItemDef`'s
   already-proven versions, and wired the check directly into `ObjectDef.load()`'s existing loop
   (reusing the same bytes already fetched for the real decode — no extra cache I/O), writing a
   summary to `OBJECT_DEF_OPCODE_DUMP.txt` on every boot.
2. Booted the server myself to get real data — no live client needed for this, since `ObjectDef.
   load()` runs at boot before any player connects, and `world_stage=DEV` in `DMS/server.properties`
   skips the SQL database connection entirely (confirmed via `World.isDev()`/`WorldStage.DEV` and
   Server.java's `if (!World.isDev())` gate around the DB-connect block). Ran `./gradlew :DMS:run`
   headless with a timeout, three separate times across the fix.
3. FIRST boot (pre-fix): 21 distinct unknown opcodes. By far the dominant one: **opcode 61, hit as
   the FIRST unrecognized opcode on 6501 objects** — meaning 6501 objects' entire byte stream past
   that point (options, sizeX/Y, clipType, recolor/retexture data, sound ids, varp-driven
   visibility, ...) was garbage before this fix, completely silently (no exception, no log, nothing
   — `LOADED.put(id, def)` still ran with the corrupted `def`). Also real: opcode 82 (357 objects —
   turned out to be Cache228's alias for the same field as the already-handled opcode 60), opcode 89
   (163 objects), opcode 249 (21 objects, the same "parameters" block format as ItemDef's own opcode
   249). The remaining ~15 opcodes each hit ≤30 objects on tiny numbers (3, 4, 6-13, 16, 20, 37, 93,
   202, 231, 246) that don't appear in any real rev-228 object decoder — see point 5 below for why.
4. Fetched AlterRSPS's live `ObjectDecoder.kt` from GitHub (`github.com/AlterRSPS/Alter`, path
   `plugins/filestore/src/main/kotlin/dev/openrune/cache/filestore/definition/decoder/
   ObjectDecoder.kt`, found via the GitHub git-trees API since code search needed auth) — same
   ground-truth source Stage 05 used for `ItemDef`, not the sibling `DeadMen/` repo (rev 184, off
   limits per project rules). Cross-checked EVERY opcode our decoder already claimed to handle, not
   just the unknown ones — this caught a second, more subtle bug: opcodes 78 and 79 (ambient sound)
   were already "known" (so the opcode-audit alone would never have flagged them) but under-read by
   exactly one byte, because Cache228 (rev228 ≥ 220) appends a `soundRetain` byte AlterRSPS's decoder
   conditions on `revisionIsOrAfter(220)` that this decoder never read.
5. Fixed all 5 real gaps: opcode 61 (`category`, new field, discarded), opcode 82 (merged into the
   existing opcode-60 `mapMarkerId` case — AlterRSPS: `60,82 -> mapAreaId`), opcode 89
   (`randomizeAnimStart`, new field), opcode 249 (parameters block, same wire format as ItemDef's —
   new `attributes` map field), and the opcodes 78/79 missing byte (read-and-discard, matching
   AlterRSPS's conditional exactly since this deployment's cache is always rev228). Also closed
   opcode 90 (`delayAnimationUpdate`, 0 bytes, 8 objects) while in there, purely for completeness —
   it was never a desync risk since it consumes 0 bytes either way.
6. SECOND boot (post-fix): 1 distinct unknown opcode left — opcode 90, which point 5 had just fixed
   in the same edit that produced this dump (stale — the dump reflects the PREVIOUS compile). THIRD
   boot (after that): **0 distinct unknown opcodes**. Server reached well past `ObjectDef.load()`
   into `DataFile.load()`/`PackageLoader.load()`/`Starting server workers...` with no new exceptions
   across all three boots — the only errors present (the ~84 region-decrypt failures, 9-11 `Package
   Failure` content gaps, one `AbyssalSire` NPE) are all pre-existing and already documented in
   THE_PLAN.txt's 2026-07-12 update section, not caused by this change. Point 3's ~15 tiny-hit-count
   "phantom" opcodes ALL disappeared once opcode 61 was fixed — confirming they were downstream
   garbage from that one desync cascading into neighboring objects' byte alignment, not independent
   bugs. Killed the diagnostic server process afterward (headless, `world_stage=DEV`, no persistent
   state written — safe to just stop).
7. **This is a broader fix than Stage 07's own symptom** — corrected object fidelity for 6501+
   objects project-wide (rendering, clipping, sound, recolor, varp-driven visibility), not narrowly
   scoped to "walk but don't interact." Added to THE_PLAN.txt's status sections too. Whether it also
   resolves THIS stage's specific symptom is unknown — none of the corrupted fields were things
   Round 1 traced as being on the `successAction` resolution path (that path reads `gameObject.
   actions`/`getDef().defaultActions`, which are code-side `ObjectAction.register` registrations,
   not cache-decoded `options`) — so hypotheses B (disproven) and C (partially weakened) from Round
   1 still stand as the more likely explanations for the original symptom. Round 1's `[OBJACTION]`
   diagnostics are untouched and still the next real lead.
