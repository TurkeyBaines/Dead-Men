## PRE-AUDIT FINDINGS (2026-07-13, agent round 1 — no live client this session)
Audited every transmit-side mapping this stage owns against the osrs-228-model sources jar
(MapProjAnim.kt, SoundArea.kt, MapAnim.kt, PlayerAvatarExtendedInfo.kt) plus the legacy callers
(Projectile.java, Entity.publicSound, PlayerMovement.force, MapDirectionUpdate, HitsUpdate,
ForceMovementUpdate, Direction). Two real bugs found and fixed, both in PacketSender.java:

1. FIXED — sendProjectile passed sourceIndex = -1 as "no source". MapProjAnim's KDoc: 0 = no
   source lock; players are -(index+1), NPCs are (index+1). So -1 actually meant "origin-locked
   to the player at index 0" — every projectile in the game would have visually snapped its start
   position to whichever player happens to hold index 0. Changed to 0. (targetIndex needed no
   change: Projectile.java already encodes 0 / ±(index+1) — exactly RSProt's convention.)

2. FIXED — sendAreaSound passed dropOffRange = distance (15). Per SoundArea.kt's KDoc,
   dropOffRange is the SIZE of the sound's origin ("in most cases, this should be a value of 1";
   larger = big-NPC footprint). 15 made the client treat the tile as the SW corner of a 15x15
   even-volume box, destroying distance falloff. Changed to 1.

Audited and confirmed CORRECT (no change made — do not "fix" these on a hunch):
- setFaceAngle: MapDirectionUpdate's player mode already stores a real 0-2047 angle
  (atan2 * 325.949 & 0x7ff).
- setExactMove: legacy 184 is OSRS-era; PlayerMovement.force's teleport-first + negated-delta
  convention is the same block semantics rev 228 uses. Delays are client cycles in both.
  Direction.clientValue is a real 0-2047 angle (S=0, SW=256, SE=1792), not a 0-3 code.
- addHitMark/addHeadBar: 7-arg addHeadBar(sourceIndex, selfType, otherType, startFill, endFill,
  startTime, endTime) matches the call; hpBarRatio is already in per-type pixel units (30/100/
  120/160), which is exactly RSProt's "pixels per headbar config" fill scale. sourceIndex=-1 IS
  the documented "none" for hitmarks/headbars (unlike MapProjAnim, where none = 0).
- setSequence/setSpotAnim/setSay/setMoveSpeed/setTempMoveSpeed: verified against KDoc tables;
  1=walk/2=run/127=teleport all match.
- MapAnim (sendGraphics): direct 1:1, delay in client cycles both sides.

## NOTES FROM OTHER STAGES
- Stage 02 (2026-07-08): found and fixed a SECOND zone-coordinate bug in
  `PacketSender.queueZonePayload`, on top of the 2026-07-07 `x & ~0x7` fix — that earlier fix was
  necessary but not sufficient. `UpdateZonePartialEnclosed`'s `zoneX`/`zoneZ` fields are `UByte`
  (0-255) and, per its KDoc's own worked example, are expected to be coordinates *relative to the
  player's 104x104 build area origin*, not raw world-absolute tile coordinates — the doc's
  "absolute, not shifted" wording only disambiguates from the divided-by-8 zone-index form, it does
  NOT mean world-space. The code was passing `x & ~0x7` directly (a world-tile value, typically in
  the low thousands), which silently truncated when narrowed to `UByte` and pointed every zone
  packet at an essentially random wrong zone. Fixed by subtracting the player's own build-area
  origin in tiles: `(x & ~0x7) - (player.buildAreaZoneX << 3)` (mirrors the already-proven-correct
  `x - (p.buildAreaZoneX << 3)` pattern `RsProt.java` already uses for `SetNpcUpdateOrigin`).
  **This affects all six `queueZonePayload` callers, i.e. everything in this stage's "Zone FX"
  checklist (B)** — projectiles, graphics/MapAnim, area sounds, and object add/remove/animate all
  had the same wrong-zone bug ground items did. If you're picking up this stage after Stage 02 is
  merged, you should be testing against the FIXED coordinate math already — if zone FX still lands
  in the wrong place, don't re-derive this fix, look for something else. If you're picking up this
  stage BEFORE Stage 02 is merged, expect every item in checklist B to fail identically to how
  ground items failed, for the same underlying reason.
- Also ported `ObjDel` (ground-item removal) and `LocAnim` (object animation) — both previously had
