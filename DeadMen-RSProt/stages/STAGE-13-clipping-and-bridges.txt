STAGE 13 — Clipping / bridge collision investigation (water pathable, bridges "don't work")
STATUS: FIXED (2026-07-14, round 2 session). ROOT CAUSE: `Region.java`'s tile-settings decode loop
(`init()`) read the per-tile opcode as a single byte, and the overlay-id payload for opcode<=49 as a
single byte. This cache generation (OpenRS2 stock 228 dump) actually encodes BOTH fields as 2-byte
values (Jagex widened them at some point to fit more overlay/underlay texture ids than a byte allows).
Reading 1 byte where 2 were written silently desyncs every tile parsed after the first wide value in
a region's byte stream — no crash, no garbage, just wrong bits landing on wrong tiles for the rest of
that region, which is exactly why blocked-flags/roof-flags/bridge-flags all "mostly worked" but were
occasionally wrong in a way that looked like scattered missing content rather than a parser bug.
CONFIRMED via a real, actively-maintained reference decoder: `Avexiis/RSPSi`
(github.com/Avexiis/RSPSi, `Client/src/main/java/com/jagex/map/MapRegion.java`) ships TWO decoders —
`decodeOldMapData` (byte-for-byte identical to what this file used to do) and `loadTerrain` (the one
actually used for this cache generation), which reads the opcode via `readUnsignedShort()` and the
overlay payload via a 2-byte read, not 1. The human independently confirmed this cache decodes
correctly in that tool (RSPSi screenshots: Z=0 showing genuine unwalkable water/hillside, Z=1 showing
the real bridge-flag tiles on the actual bridge deck) BEFORE this fix was found — that visual proof is
what pointed straight at the byte-width bug instead of a content gap.
FIX: `Region.java init()` — changed `mapIn.readByteUnsafe() & 0xFF` to `mapIn.readUnsignedShort()` for
the opcode, and `mapIn.skipByte()` to `mapIn.skip(2)` for the opcode<=49 (overlay) branch. Nothing else
in the loop changed — the 49/81 thresholds, the tileFlags storage, and the height-marker (opcode==1)
single-byte read are untouched (per the fork's decoder, only the opcode and overlay payload widened).
Compiled clean, human confirmed live: Falador's bridge now works, walking into the water next to it is
now blocked, and multiple previously-reported "objects that weren't there" (Barbarian Village's log
balance/obstacle-net area, and others) started resolving correctly too — this was a single shared root
cause behind the whole class of "some objects/clipping missing" symptoms in THE_PLAN.txt's 2026-07-12
"11 real content gaps" list, not 11 separate gaps. Region.java is otherwise unchanged.
CORRECTION to Round 1 below: that attempt was on the right track (same file, same idea: opcode width
mismatch) but only widened the overlay-payload read while leaving the OPCODE read at 1 byte — a
half-fix that desyncs the stream even further (reads garbage for both what-the-opcode-is AND
its payload), which is exactly why it made things worse elsewhere instead of fixing anything. Widening
BOTH together (this fix) keeps the stream aligned.
This file's prior "BLOCKED / INVESTIGATION ONLY" state and everything below is kept for the trail —
read it if you want the reasoning, but the fix above is the actionable answer.

## ROUND 1 — byte-width hypothesis (TRIED, REVERTED, CAUSED A LIVE REGRESSION)
Compared `Region.java`'s map-tile-settings byte parser against `rsmod/rsmod` (the engine Alter is
"a modified version of", per Alter's own repo description) — specifically
`api/cache/src/main/kotlin/org/rsmod/api/cache/map/tile/MapTileDecoder.kt`. Its `decode(buf:
ByteBuf)` function reads:
  - `opcode <= 49` → `buf.readShort()` (2 bytes) for an overlay id
  - `opcode <= 81` → rule = opcode-49, no extra read (matches this project already)
  - `opcode > 81` → `id = opcode - 81`, **no extra buf read at all** (computed straight from the
    already-consumed opcode byte)
This project's original code does `mapIn.skipByte()` (1 byte) for `<=49` and does **nothing** for
`>81` (falls through the if/else-if chain as a silent no-op, net effect identical to "no extra
read" — which, per the above, is actually correct for the `>81` case).

Changed ONLY the `<=49` branch from `skipByte()` to `skip(2)`, matching rsmod. Compiled clean.
**Live-tested by the human and it made things WORSE** — new invisible walls appeared in open paths
in an unrelated area (a custom tournament/DMM arena baked into a high-Y "instance template" region,
~x=3806,y=9757, region 15256 — screenshot showed a red-annotated "INVISIBLE WALL" mid-corridor).
**Reverted immediately.** Root of the mistake: no confirmation that rsmod's CURRENT `main` branch
targets the same cache generation as this project's actual `Cache228` (a Feb-2025 OpenRS2 dump of
rev 228 specifically). rsmod is a live, continuously-updated engine; Jagex has added large numbers
of new overlay/underlay texture ids over the years and very plausibly widened that field at some
revision AFTER 228. Comparing against rsmod's latest source may silently be comparing against a
newer wire format than this cache actually uses. **Do not blindly trust rsmod's current source as
a stand-in for "what Alter/228 does" — go to Alter's own repo, and ideally pin to a specific
commit/tag if one exists close to a 228-era timeframe, not just `main`.**

## ROUND 2 — empirical buffer-alignment check (INCONCLUSIVE, but informative)
Before touching anything live again, wrote a throwaway simulation (in `Region.getMapData()`,
temporary, removed after) that replays the exact same tile-settings byte stream under 4 hypotheses
(overlay skip = 1 or 2 bytes, underlay skip = 0 or 2 bytes) and reports how many bytes of the
decompressed buffer are left over after all `4*64*64 = 16384` tiles terminate.

Real data pulled via this project's own `IndexFile`/`FileStore` (region 11828 = Falador, archive
name `m46_52`, archiveId 4002, `validFilesCount=1` — single-file archive, ruling out an
IndexFile.cacheArchiveFiles multi-file-slicing bug; compressed 6229 bytes, decompressed 70976
bytes; region 15256 = the tournament arena regressed in Round 1, archiveId 2976, compressed 2079,
decompressed 95862):

| overlaySkip | underlaySkip2 | region 11828 finalPos/70976 | region 15256 finalPos/95862 |
|-------------|---------------|------------------------------|-------------------------------|
| 1 (current) | false (current)| 33525 (37451 leftover)      | 46011 (49851 leftover)        |
| 2           | false          | 32611 (38365 leftover)      | 36864 (58998 leftover)        |
| 1           | true           | 49353 (21623 leftover)      | 70369 (25493 leftover)        |
| 2           | true           | 45150 (25826 leftover)      | 51926 (43936 leftover)        |

**None of the four hit an exact match** (tiles-terminated was 16384/16384 in all four cases with
zero exceptions — the loop never runs off the buffer end under ANY hypothesis, because zero bytes
are common enough in real terrain data that every hypothesis trivially finds "a" terminator per
tile; this makes "does it complete without crashing" a useless discriminator). Checked whether the
leftover region was pure zero-padding (which would mean the decompressed buffer is just
oversized/padded and leftover is a non-bug) — it is NOT: 25-35% of the leftover bytes are non-zero
in every variant, meaning there is real, structured, un-parsed content after wherever each
hypothesis stops, regardless of which hypothesis is used. **This rules out the simple "declared
decompressed length is padded" explanation too.**

Manually hand-traced the first ~109 bytes of Falador's raw decompressed map data (hex dump
preserved below) against the CURRENT/ORIGINAL single-byte scheme. It decodes into a clean,
sensible, exactly-repeating 11-token pattern (`90 00 01 28 00 02 00 7B 00 35 00`, repeating
identically ~6 times in a row — entirely plausible as a uniform floor/wall texture run in a
courtyard), with no contradictions or garbled tile boundaries. **This is the strongest single piece
of evidence that the ORIGINAL single-byte parser is likely correct**, and that Round 1's "fix" was
comparing against the wrong wire-format generation. Combined with fact #2 above (flag semantics
verified against Alter itself, not just rsmod), the working theory going into the next session
should be **"the tile-settings parser is probably fine; something else is missing/wrong"** —
almost certainly a genuine content gap (a fence/wall object that should exist in this exact stock
Cache228 dump and doesn't, OR exists but has a decode bug specific to it) rather than a systemic
byte-format bug. This would be consistent with THE_PLAN.txt's own 2026-07-12 entry documenting
~11 other real-content object/tile references that don't resolve against this exact stock cache
snapshot (GWD, Motherlode Mine, Revenant Caves, Wintertodt, agility courses, etc.) — Falador's

class.

## OTHER THINGS CHECKED, RULED OUT
- **Multi-file archive de-interleaving bug in `IndexFile.cacheArchiveFiles`**: ruled out —
  `getValidFilesCount` reports exactly 1 for both test regions' map archives, so the
  `filesCount <= 1` fast path is what actually runs (no de-interleave logic involved at all).
- **XTEA encryption on "m" (map/terrain) archives**: not applicable — only "l" (landscape/object)
  archives are XTEA-encrypted in the real OSRS format; `getMapData()` correctly never passes keys.
  This matches known-correct behavior, not a bug.
- **`FaladorCourse.java`** (the rooftop agility course through the same castle) was checked for any
  existing manual clip patch near the moat that might hint at a known-good fix — it operates at
  z=3 on the roof (coords ~x=3010-3050,y=3330-3365), unrelated to the ground-level moat at
  z=0/x=2955-2965. No direct precedent found there.
- **`::pos`/`::clipping` admin commands**: while getting repro coordinates from the human, found
  bare `::pos` throws `Cannot load from object array because "args" is null"` — `CommandHandler.
  handle()` sets `args = null` when the command has no trailing space (`io.dm.network.incoming.
  handlers.CommandHandler.java:69`), and `MapCommands.process()` immediately does `switch(args[0])`
  with no null guard. **This is a real, pre-existing, unrelated bug** (you must type `::pos pos` /
  `::pos clipping`, not bare `::pos`/`::clipping`, or it NPEs and prints nothing useful) — not fixed
  in this investigation, flagging it here since it wastes a human's time during live-testing if
  they don't know the workaround. Cheap, safe, out-of-scope fix if you want to pick it up: null-
  guard `args` in `MapCommands.process` (or default it to an empty array in `CommandHandler.
  handle()` instead of `null`).

## WHY NOT JUST PATCH IT (read before reaching for `flagUnmovable()`)
The human explicitly pushed back on a manual per-tile patch: "surely this is flagged as unwalkable
in the cache? we can't hard code every single thing... Surely something isn't mapping properly."
Their concern is legitimate — if this is one symptom of a systemic mapping problem, patching this
one spot fixes nothing else and leaves the real bug live elsewhere (every other bridge/moat/water
edge in the game is unverified). **Before patching Falador specifically, form a view on whether
this is isolated or systemic** — e.g. check a second, unrelated, well-known bridge (Lumbridge's
river bridge was the planned next check this session, region should be ~12850 given baseX/baseY
math off (3222,3217), NOT executed — an edit for a `[LUM_CLIP]` diagnostic was drafted but the
human interrupted before it was compiled/run, so it was reverted untested). If Lumbridge (or
another simple, iconic bridge) shows the exact same "blocked flag exists above z=0, nothing at
z=0, no bordering wall object" pattern, that's evidence of a systemic issue worth chasing further
upstream (maybe in how `l`/object data or a specific object class's `clipType` gets decoded — see
Stage 07's already-documented `ObjectDef` opcode-desync bug for a precedent of exactly this shape
of systemic issue, fixed for options/size/clip/colour fields but conceivably incomplete). If
Lumbridge is clean, that's evidence Falador's moat specifically is a stock-cache content gap (like
the ~11 already-documented ones in THE_PLAN.txt's 2026-07-12 section) and a targeted
`flagUnmovable()` patch — the same pattern already used all over this codebase — is the
appropriate, low-risk fix for this one spot, not a sign of surrender.
